# Roadmap from 2026-09-22: checks first, the verdict first, drawings next

Written after the pilot workstation's evening GUI packet
(`docs/pane-findings-2026-09-20-review-gui.md`, asks U8 to U16) and the owner's direction of
2026-09-22. It replaces nothing in the feature packages; it says what is built next, in
what order, and why. Each feature below gets its own Spec Kit package when it starts.

## What the evidence says

**Token cost is resent tool output, not model work.** The big assembly's review billed 12.4M
input tokens over 41 rounds for 99 findings. 95.7% of every request was earlier tool results
that stay in the conversation for the rest of the review; 96.7% of input was served from the
cache, so only 407k tokens were new. One `check_rms_part` result of about 205k tokens was
resent roughly thirty times and is 51% of the bill on its own. `list_mates` is another 14%,
and 78% of its bytes are internal reference strings the model never uses. A 13-token
follow-up question cost 405k tokens because the whole history went again.

**Most of the review is work code can already do.** 90 of the 99 findings came from checks
that take no arguments: the three modelling-practice families and the standards family. The
remaining nine were interference groups found by a live detection call and three hole
alignments with no tolerance. An offline replay of the recorded calls through the current
code reproduces the observed tokens within 0.5%, so savings can be measured without a seat
or a key.

**The goal checks have gaps no amount of model rounds closes.** On the big assembly: the 68 screws
were not recognised as fasteners (only Toolbox parts count), so an M4 screw in an M5 tapped
hole went unreported; four of the ten "Start here" slots across the two evening runs were
zero-volume size-for-size contacts reported as interferences; the model checked unrelated
hole pairs for alignment while five real candidates exist, one with a 0.75 mm dowel offset;
the mass-override read throws on every part; the model carries no tolerance at all; tool
access is a measurement nothing calls.

**No drawing can be extracted live.** Since 2026-09-18 the attach refuses a drawing before
it asks for a configuration, so the drawing phase has only ever run under test fakes, the
Standards tab fails on a drawing, and no review has seen a sheet. Every evening review asked
for drawings and left fits, stacks, alignment and manufacturing inputs unresolved.

**The pane still reads like a developer tool.** The previous review stays on screen when
another document opens, findings open as paragraphs, 94 of 99 findings sit past a top five
with no way to reach them, and the screen shows check ids, component ids, status tokens and
JSON.

## Decisions taken 2026-09-22

| Question | Decision |
|---|---|
| How the efficiency work ships | All four changes become pane defaults - model-facing payload slimming, checks first, history pruning, and parallel tool calls - gated by the offline replay showing the same findings and a token cut on every recorded run. This supersedes the rule that no pane default changes before a held-out design. |
| Modelling-practice findings in Review | One folded group ("Modelling practice: 85 findings across 12 rules"), collapsed, the full list one click away; the model reads counts only; Model check stays the tab to work them |
| Where tolerances come from | All four sources, read in this order of availability: Hole Wizard fits and thread classes, model dimension tolerances and DimXpert/MBD annotations, drawing callouts, and a general tolerance block. A missing tolerance stays unresolved; none is guessed. |
| Drawing work before the next test | Read-only context: fix the attach, attach open drawings, extract dimensions, tolerances, notes and tables, a per-part drawing brief, and pane questions. Creation is specified after seat probes and a constitution amendment. |

## The features, in order

### 008 Checks-first review and the token budget

The architecture change the rest builds on: **code runs every check it can enumerate, the
model explains, asks and investigates what code cannot scope.**

- An offline replay harness (`swreview benchmark replay <run>`) that re-runs a recorded
  session's calls through current code and reports tokens per round and the finding set. It
  is the gate for every change below.
- Model-facing payload slimming: internal reference strings out of what the model reads
  (short ids resolved server-side for the two bridge tools), compact JSON, check tools that
  return a digest (counts, statuses, finding ids) with a detail tool on demand, gap rows
  grouped by reason.
- Checks first, always on: the modelling-practice, equations, assembly, standards and
  interference families run in code before the first model turn, the live interference
  detection included; the interference rows are persisted into the run's package.
- History pruning: a tool result older than one or two rounds is replaced by a short
  deterministic stub; the full payload is written to the run folder, so nothing becomes
  uninspectable.
- Parallel tool calls on in the pane.
- Evidence answers batched into one resumed turn; the cached and uncached split shown
  honestly.
- Modelling-practice findings folded into one group in the ranking and the report.
- Target, measured by the replay: the big assembly from 12.4M to under 1M input tokens and
  the small assembly from about 1.5M to under 0.3M, with every recorded finding still produced.

### 009 The engineer's workspace

The pane for someone who is not a developer, from U8 to U15, in increments that each ship:

1. Right model on screen: the review hides itself when another document opens, a Clear
   review control, the header shows the file name; the Remodel banner in plain words (U8,
   U13).
2. Headlines, not paragraphs: findings default to one line; the evidence moves into the
   fold; a Start-here click scrolls instead of opening; Collapse all (U10).
3. Nothing hidden past five: every issue reachable in policy order behind "Show all", with
   a "5 of 18 issues" count; the duplicated Start-here renderer becomes one shared script
   (U12).
4. The first ten seconds: a summary at the top - decisions only you can make, things to
   fix, things to verify, questions for you, parts not loaded, and which of the check goals
   were not reached and why - computed by the backend, printed verbatim.
5. Questions for you: open evidence requests as one short question at a time above Start
   here, answers sent together (U15).
6. Results or Transcript: one view owns the pane (U11).
7. Per-model sessions: chips per reviewed document and configuration, restorable (U9).
8. Plain language throughout, and the same document binding on Model check and Standards.

### 010 Automatic mechanical checks

The owner's goal list, each made a deterministic check that code enumerates:

- **Static interference**: every detected group judged, zero-volume contact reported as
  contact, not interference.
- **Joint map**: hole to hole, pin to hole and screw to tapped hole pairs found from the
  geometry; the basis for the next three.
- **Hole alignment and the stack-up**: nominal alignment from the joint map (offset against
  half the clearance), the position budget as a recommended callout, and the worst-case
  stack-up once tolerances are read; the existing diameter-versus-radius comparison fixed.
- **Fastener thread engagement**: fasteners recognised beyond Toolbox (file name and
  description parsing, cross-checked against the measured shank), thread match, engagement
  and bottoming from the placed geometry.
- **Tool access above screw heads**: a real check from the joint map's head plane, a tool
  per head type, and counterbore head fit.
- **Mass and material for all geometry**: the mass-override read fixed, density against the
  named material, assembly mass overrides flagged, unread and surface-only bodies counted.
- **Hygiene**: part-number property against the file name, duplicate descriptions and part
  numbers, missing revisions, suppressed and lightweight components as findings.
- **Tolerances**: Hole Wizard fit and thread class and the drill, counterbore and countersink
  sizes; model dimension tolerances; the general tolerance from the profile; drawing
  tolerances from 011.

Every new check joins 008's code-first pass automatically, so it costs no model rounds.

### 011 Drawing context, read only

- The drawing attach fixed, so a drawing root dumps and Standards grades drawings live.
- The read-only guard hardened against every drawing and tolerance setter first.
- Drawings already open in SOLIDWORKS whose views reference a reviewed document attached to
  part and assembly reviews; a gap recorded when none is open; a same-name drawing next to
  the part offered as a question, never opened silently; the vault never walked.
- Native display text, tolerances, hole callouts, datums, geometric tolerances,
  surface-finish symbols, and BOM, hole, general-tolerance and title-block tables extracted.
- A per-part drawing brief, bounded and served on demand: what the part is, how it is
  assembled, which interfaces need a callout, what the existing drawing covers, and the
  engineer's confirmed answers.
- A `drawing` section in the standards profile: template, sheet format, drafting standard,
  projection, general tolerance, BOM template.

### 012 Drawing creation (later)

Specified after 011 and seat probes: an LLM-proposed drawing plan per part that the engineer
reviews (citing real model entities, never inventing numbers), then a gated creator that
writes a new drawing into the run folder only, behind a constitution amendment for a third
write path. SOLIDWORKS 2024 has no auto-generate drawing API, so the creator is rule-based
by part class, as ADR-001's fallback says.

### Start from the existing drawing-creation base, not from scratch

**The owner has an outline and base repository for programmatically creating SOLIDWORKS
drawings (noted 2026-09-22). Drawing work in 011 and 012 starts from it.** Before any
specification of drawing creation is written, and before any drawing-writing code is added
here, the first task is to read that repository and record what it already does:

- which drawing operations it performs (template and sheet setup, view creation and
  placement, model-annotation import, dimensions, BOM and balloons, notes) and on which
  part classes;
- which SOLIDWORKS version and API members it uses, and which of them the 2024 SP5 interop
  on the pilot seat exposes;
- how it chooses views and dimensions (rules, templates, or none), and what inputs it
  expects - which tells 011 what the per-part drawing brief must contain;
- how it is licensed and packaged, and whether it is reused as a library, ported into
  `extractor/`, or kept separate and fed a drawing plan from this product;
- how it would sit behind this product's write rules: a new file in the run folder only,
  nothing overwritten, an allowlisted gate, every operation logged.

The outcome is a short evaluation beside the 012 specification, and 012's plan is written
against it: reuse what works, and build only what it lacks. The owner's own flat-pattern
drawing macros (`Flat Pattern Drawings` v0.1 and v1.1 in the local SOLIDWORKS macro folder)
are prior art of the same kind and are read in the same pass. **Location of the base
repository: to be supplied by the owner.**
