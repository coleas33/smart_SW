### Note: the findings differ from 2026-09-18, and the reason matters

The handover's expected order for this assembly was the two `interference.static` rows
first, then the three RMS rows. **This run produced no interference findings at all.**

```

{"status":"computed","configuration":"Default","interferences":[],"added_to_package":0,"gaps":[]}
```

The difference is that **both dowel-pin instances were lightweight on this run**. The
coverage section names it 20 times, for example:

> `rms.folders.present` - pin instance lightweight; tree not read

so the pins contributed no geometry, no holes and no Toolbox identity, and the package
carried **23 extractor gaps**. On 2026-09-18 the same assembly produced two
`interference.static` findings.

**This is worth upstream attention even though it is not a Task A failure.** The same
assembly, the same commit and the same model produce a materially different review
depending on whether SOLIDWORKS has the components resolved or lightweight, and nothing in
the headline says so - it takes reading the coverage section to discover that the two
components the assembly exists to locate were never examined. Candidates: resolve
lightweight components before the dump, or raise the lightweight state to the verdict line
rather than leaving it in coverage detail.

## Issues found today

### Issue 1: a flaky test in the add-in regression gate

`dotnet test extractor\SwReview.sln -c Release` failed **1 of 1208** on the first run and
passed **1208 of 1208** on an immediate re-run of the same binaries, with no other change.
The failing test's name was not captured before it went green, so it needs catching the
next time it trips.

This matters because the suite is the update gate in `update-workstation.ps1`: a flaky
member makes a red gate ambiguous.

### Issue 2: the standards profile holds example values

`%LOCALAPPDATA%\SwReview\standards.yaml` was missing, so the Standards tab refused with

```
the standards profile at '...\standards.yaml' could not be opened (Could not find file ...).
Check `StandardsProfilePath`.
```

This is designed behaviour (feature 006 has no fallback; task T100 assigns the profile to
the owner), not a defect. The file was created from `config/standards.example.yaml` and
`load_profile` accepts it, so the tab now runs - but **every value is fictional**, so any
Standards verdict from this machine is meaningless until the owner replaces them from
the owner's standards source. Task C's result is gated on this.

Suggestion: the tab could say "no profile configured - see runbook section 5" rather than
surfacing a file-not-found and a settings key name, since every first run hits this.

### Issue 3: lightweight components hollow out a review, and the engineer cannot act on it

Raised as a feature request: **`feature-request-resolve-lightweight.md`** in this folder.

Short version: both dowel pins were lightweight on every run today, so live interference
returned nothing where 2026-09-18 found two `interference.static` findings, 23 extractor
gaps were recorded, and seven of sixteen Standards checks went unresolved. The Standards
tab says so clearly; the Review tab leaves it in coverage detail. The engineer is given no
way to resolve the components and re-run, because `SetSuppression2` is on the
`ReadOnlyGuard` denylist by design.

The request asks for a per-component resolve table with resolve-all and resolve-none,
built on the suppress-test's gated-mutation precedent rather than by touching the denylist
- and notes a cheaper first increment (detect and warn) that needs no mutation at all.

### Issue 4: `update-workstation.ps1` cannot run on this machine's branch

The script performs `git pull --ff-only origin main` at step 3. This workstation works on a
`local` branch that carries machine-local documentation commits (the two-lane arrangement
in `AGENTS.md`), so the pull cannot fast-forward and the script stops before the build and
the gates.

Steps 4 to 7 were run by hand with identical commands. Either the script should detect a
non-`main` branch and skip its own pull with a message, or the runbook should say it
requires `main`.
