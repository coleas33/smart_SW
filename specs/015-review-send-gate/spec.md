# Feature Specification: Send the Review to the Model Only When the Engineer Wants It

**Feature Branch**: `015-review-send-gate`

**Created**: 2026-10-08

**Status**: Draft, revised twice on 2026-10-08: after an adversarial review of the first draft, and again after a second review of the revision (the re-run after a restart, the opening's words, the departures from earlier features). Touched once more on 2026-10-09 by the plan's adversarial review: the key a carried decision is matched by (FR-029), an apply that fails while a review waits (FR-020), what a reload during a re-run shows, and SC-010's note on folded findings. Touched again the same day by the plan's second review: a Send that fails before any request, where the Send block sits (measured, FR-034), the Standards profile across a restart, a drawing outcome an unfinished read loses (FR-021), and the commit a labels regeneration lands in (FR-035). The owner's decisions 59A to 62A (2026-10-08) set the shape. Every other question is settled by a default taken on 2026-10-08, which the owner may revise (Assumptions). Three of those defaults change what gets built, so they were also put to the owner as questions 2 to 4; each is marked where it applies. Question 1 of the first draft (whether answers and decisions carry across a restart) is withdrawn: 61A decides it.

**Input**: The owner's request of 2026-10-08, verbatim: "I want the option to not send the review to llm after clicking review. Give me a checkbox to auto send to llm after done or not or send after approval if that is not already planned." It was not planned anywhere: specs 001 to 014, `docs/` and the history were checked on 2026-10-08. Today the code checks and the model's first turn are one step. Starting a review runs extraction, part roles and the checks-first pre-run (feature 008), and then submits the model's first request before the pane hears that the review has started. Stop cannot prevent that first request. With no key in Settings or the environment, the review fails before any check runs.

**Owner decisions (2026-10-08)**:

- **59A**: one checkbox, "Send to the model when the checks finish", ticked by default, so today's behaviour is unchanged. When it is unticked, pressing Review runs the code checks only (extraction, part roles, the checks-first pre-run of feature 008) and stops. The Review tab then shows a "Send to model" button, which is the approval, together with the estimated size of the first model request in tokens. Cost is in tokens, not currency (feature 008). Feature 009 FR-016's resume-cost sentence is the precedent, including its wording when the size cannot be measured. Never pressing Send means nothing about this review reaches the model. A checks-only review must work with no API key stored.
- **60A**: the checkbox sits on the Review tab beside the Review button, where it can be seen, not inside Settings. It is remembered across sessions, and changing it does not restart the backend. It must fit the pane's layout budget: 260 to 420 px wide, the session buttons in two rows at 300 px, and the summary inside a 300 by 600 viewport. It must also follow the pane design system: the shared tokens, the existing checkbox style, no literal colours, the page's script and style rules, and text set only as text.
- **61A**: Send resumes the same paused review. Part-roles answers and Accept/Reject/Defer decisions made while it waited are kept. Answers given while it waits are regraded by code with no model call. The model's opening message (package brief and pre-run digest) reflects any regrade done before Send. If the backend restarted in between (a Settings save restarts it; SOLIDWORKS was closed), Send re-runs the checks from the same run folder, with no re-extraction, and then sends.
- **62A**: delivered as new speckit feature 015 (spec, plan, tasks) on its own branch. The work is test-first, gets an adversarial review, passes a gate that includes the add-in tests, and has one licensed-seat check on the pilot workstation (a [W] task).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Review Without Sending Anything to the Model (Priority: P1)

An engineer unticks "Send to the model when the checks finish" beside the Review button and presses Review. The review reads the SOLIDWORKS model and runs every code check a review runs today before the model is asked anything: extraction, part roles and their question, the checks-first pre-run, and the drawing questions. Then it stops. The Review tab shows the result as it shows a finished review: the summary, the questions, the findings grouped by type, and the coverage. The status line reads "Checked by code. Not sent to the model.", and a Send to model button is offered. Nothing about the review has reached a model provider, and nothing will unless Send is pressed. No API key is needed. The box keeps its setting the next time SOLIDWORKS starts.

**Why this priority**: the request was for the option not to send. A review the engineer can run without the model, at no token cost and with no key, is the whole of that option. It also makes the code checks usable on their own on a seat with no key.

**Independent Test**: a provider stand-in fails the test if it is ever set up or asked anything, and no key is in Settings or the environment. An unticked review of a fictional fixture assembly then shows the same findings and questions that the same review shows today just before its first model request. Its coverage holds the same rows plus exactly the rows the end of the checks adds: the close-out row, one unresolved row per open question, and one "not sent to the model" unresolved row per checklist item only the model closes. Its report says it was not sent to the model. The box reads unticked after the pane is reloaded and after a new SOLIDWORKS session. Changing the box neither restarts the backend nor touches any other setting.

**Acceptance Scenarios**:

1. **Given** the box unticked, **When** the engineer presses Review, **Then** the code checks run and the review stops without any request to a model provider: no first turn, no explanation pass, no request of any kind.
2. **Given** no key in Settings or the environment and the box unticked, **When** the engineer presses Review, **Then** the review completes as checks only and shows its findings; nothing asks for a key until Send.
3. **Given** a checks-only review that has finished, **When** the engineer reads the Review tab, **Then** the status line says "Checked by code. Not sent to the model.", Send to model is offered, the follow-up box is disabled and says the review has not been sent, and Stop is not offered.
4. **Given** a checks-only review, **When** its report is opened, **Then** the report says the review was not sent to the model and names no model or provider as if one had run. Each checklist item that only the model closes is unresolved and says the review was not sent.
5. **Given** the engineer changes the box, **When** SOLIDWORKS is restarted, **Then** the box shows the changed value. The change did not restart the backend, was never refused, and left every other setting as it was. A change made while a review's extraction or checks run shows on the page at once and is saved as soon as they finish; the running review keeps the value it started with.
6. **Given** the box ticked (the default), **When** the engineer presses Review, **Then** the review is exactly today's, its failures included: same requests, same events, same results.

### User Story 2 - Send the Review When Ready, Knowing Its Size (Priority: P2)

The engineer has read the checks-only result and decides the model should see it. Beside Send to model, one sentence gives the estimated size of the model's first request in input tokens, counted on this machine without the network. It says that this is the first request's size only, and that the requests after it are not counted in advance. When the size cannot be counted, the sentence says what Send does and gives no number, as the resume sentence of feature 009 does. Pressing Send resumes the same review in the same run folder, with no new extraction and, unless the backend has restarted since (User Story 4), no re-run of the checks. The model is told what it would have been told had the review been sent at once, plus what the engineer answered while it waited. From then on the review behaves as any review does today: turns, Stop, the model's questions, the explanation pass and follow-ups.

**Why this priority**: an option to approve the send is only useful if the approval states its cost and loses nothing the checks found. It comes second because User Story 1 is useful without it: an engineer can always press Review again with the box ticked.

**Independent Test**: on a fictional fixture with a scripted provider, an unticked review then Send makes requests byte-identical to those of a ticked review of the same package. The sentence before Send gives the counted size of exactly that first request and says later requests are not counted. With the local token vocabulary absent, the sentence carries no number. With a Gemini provider it carries the counted number and says the figure is approximate, because Gemini counts tokens its own way. With no usable credential, Send is refused before any request and the review keeps waiting.

**Acceptance Scenarios**:

1. **Given** a review waiting for Send, **When** the engineer reads the Send block, **Then** one sentence states the estimated input tokens of the first model request and that later requests are not counted in advance, or says what Send does without a number when the size cannot be counted. With a Gemini provider the number is shown and called approximate.
2. **Given** a review waiting for Send with nothing answered while it waited, **When** the engineer presses Send, **Then** the model's first request is byte-identical to the first request an auto-sent review of the same package makes.
3. **Given** Send pressed, **When** the model's first turn ends normally, **Then** the explanation pass runs as it does today, and the follow-up box is enabled.
4. **Given** no usable credential (no key in Settings or the environment, and for Gemini no enterprise project), **When** the engineer presses Send, **Then** Send is refused before any request, saying no key is available and that saving one in Settings is the way on, and the review keeps waiting.
5. **Given** a key the provider rejects, an unknown model, or no network, **When** Send's first request fails before the model has answered (no model round completed), **Then** the code results stay as they were, the reason is shown beside Send to model, the attempt and its reason are recorded, and Send is offered again.
6. **Given** a review sent after waiting, **When** its report is opened, **Then** it says when it was sent, and the time spent waiting is not counted as the review's running time.

### User Story 3 - The Engineer's Work While It Waits Is Kept (Priority: P3)

While a review waits for Send, the engineer works on it as on any finished review. Answering the part-roles question regrades the review by code, with no model call. Answering a drawing question has the drawing read by code where the seat allows it. Accepting, rejecting or deferring a finding is saved. When Send is pressed, all of it is kept. The model's opening reflects the regrade. No withdrawn finding is named in it. The answers and the drawing outcomes are in it, each stated as a fact code has already applied, with no instruction to re-run a check or to continue: the model never asked these questions, and code has already graded the checks again. The line a resumed review adds naming the findings an answer withdrew is left out, because the model never saw those findings.

**Why this priority**: the pause is where the engineer has time to answer the questions the checks raise. Losing those answers, or telling the model about findings the answers withdrew, would make waiting worse than not waiting.

**Independent Test**: on the part-roles fixture of feature 013, an unticked review leaves the part-roles question open. Answering "All bought" while it waits withdraws the unclear part's modelling findings with no provider request, and the size sentence is recounted. A Reject on another finding is saved. After Send, the model's first request names none of the withdrawn findings. It carries the answer as one line saying code has applied it, with no "withdrew" line and no instruction to re-run a check or to continue, and the Reject is still on its finding.

**Acceptance Scenarios**:

1. **Given** a waiting review with the part-roles question open, **When** the engineer answers it, **Then** the review is regraded by code as an answer regrades it today, no request reaches a model provider, and the Review tab, the report and the size sentence show the regraded review.
2. **Given** a waiting review, **When** the questions panel is shown, **Then** its button reads "Apply answers" and its sentence says the answers regrade the review by code and nothing is sent to the model.
3. **Given** a decision (Accept, Reject or Defer) made while a review waits, **When** Send resumes the review, **Then** the decision is still on its finding and is treated from then on as a decision made between turns is treated today.
4. **Given** a regrade while waiting, **When** Send is pressed, **Then** the model's opening names no withdrawn finding, names every finding still standing, and carries the engineer's answers and any drawing outcomes, each stated as already applied by code. It has no line naming the withdrawn findings and no instruction to re-run a check or to continue.
5. **Given** a waiting review, **When** the engineer presses Review again or Clear review, **Then** the waiting review is kept among the kept reviews, marked as not sent, and can still be sent when it is shown again.

### User Story 4 - A Waiting Review Survives a Restart (Priority: P3)

The engineer leaves a review waiting and then saves Settings, which restarts the backend. A common reason is to enter the key that Send needs. Or SOLIDWORKS is closed and opened again later. The waiting review is still there, still not sent. Its questions, decisions and Send stay usable (default, question 4). Whichever of them the engineer uses first re-runs the code checks on the same run folder's saved evidence, with no re-extraction, no read of SOLIDWORKS and no model call. The live interference detection the first run made is not made again: its recorded outcome is carried, so the re-run tells the model what the first run would have told it. The answers and decisions made before the restart are carried onto the re-run (61A), drawing answers included, each matched to its question or finding by what it says, never by its number, and anything that no longer applies is named. The review is then a live waiting review again, and Send sends it. Once sent, it can read SOLIDWORKS live as any review of the active document can.

**Why this priority**: entering a key is a Settings save, and a Settings save restarts the backend. Without this story, the most common way into Send (no key yet) would lose the waiting review, or freeze the answers 61A says are regraded by code while it waits.

**Independent Test**: with fakes, a waiting review survives a backend restart with three things on it: a part-roles answer, a drawing answer whose read moved the finding and question numbers, and a Reject. Send then re-runs the checks in the same folder and keeps the earlier record beside the new one. It extracts nothing and makes no bridge call before the first request, and its interference digest line and coverage rows equal the first run's. It carries both answers onto their own questions, the drawing answer's outcome line included, and keeps the Reject on its own finding. Only after that does it make its first request, with the live SOLIDWORKS tools attached. With nothing answered, that first request is byte-identical to the one the live waiting review would have made. Applying an answer to a restored review instead re-runs the same way, with no provider request. A re-run that fails, and one killed part way, each leave the earlier not-sent review as the one restored, still sendable. With the restart simulated as a new SOLIDWORKS session, opening the reviewed document brings the review back with Send offered.

**Acceptance Scenarios**:

1. **Given** a review waiting for Send, **When** the engineer saves Settings, **Then** the save is not refused because of the waiting review. It is refused only while answers are being applied, a Send is in flight or a re-run runs, as a save is refused while a turn runs. The Settings section said beforehand, in one line, that saving restarts the backend and that the review's next answer, decision or Send will check its saved evidence again first.
2. **Given** a waiting review whose backend has restarted, **When** it is shown, **Then** one line under the status line says it is shown from its run folder, names the date and time its checks ran, and says that the next answer, decision or Send checks its saved evidence again first. Follow-ups stay off. The sentence beside Send says Send checks the saved evidence again before starting the model's review, without a number. A waiting review on screen when a Settings save restarts the backend moves to this state at once, without being chosen again.
3. **Given** that review, **When** the engineer applies an answer or makes a decision (default, question 4), **Then** the checks re-run on the same folder's evidence with no re-extraction, no read of SOLIDWORKS and no model request. The earlier record's answers and decisions are carried onto the questions and findings that say the same thing, and any that no longer apply are named in one line. The new answer or decision is then applied, and the review is a live waiting review again with its size sentence counted.
4. **Given** that review, **When** Send is pressed before anything else, **Then** the same re-run happens first, and only then is the model's first request made, with the live SOLIDWORKS tools attached as for any review of the active document.
5. **Given** SOLIDWORKS closed while a review waits, **When** SOLIDWORKS is reopened and the reviewed document is opened, **Then** the Review tab brings back that document's newest review if it was never sent or its send failed, with Send offered (default, question 2).
6. **Given** a re-run running, **When** the engineer tries a Settings save, Review, another review's chip, an answer, a decision or Send, **Then** each is refused as it is while a turn runs, and the status line says the saved evidence is being checked again.
7. **Given** a re-run that fails, or is cut off by a crash or SOLIDWORKS closing, **When** the review is shown again, **Then** the earlier not-sent record is the one shown, with its questions, decisions and Send still usable and its carried answers and decisions intact, and the failed attempt is kept beside it in the run folder. Nothing is sent.

### Edge Cases

- **What "no usable credential" means**: the provider cannot be set up with the settings in effect. That is no key in Settings, none in the environment, and, for Gemini, no enterprise project. A key from the environment (Settings already says "the key in this workstation environment will be used"), a Gemini enterprise project with no key, and the scripted provider all count as usable, and Send is never refused for them.
- **No usable credential, box unticked**: the review runs the checks and waits; no provider is set up, and no key is needed. Send is refused before any request, saying no key is available. After a key is saved, the backend has restarted, so Send re-runs the checks from the folder and then sends (User Story 4).
- **No usable credential, box ticked** (default, question 3): as today. The review fails before any check runs and shows today's error card. Today's Settings note, "No key is stored. Reviews will fail until one is entered.", is no longer true for an unticked review. It becomes a sentence that is true either way: with the box ticked a review fails until a key is entered, and with it unticked the code checks run and Send waits for a key.
- **The box changed while a review runs or waits**: only the next review is affected. Unticking does not stop a running review (Stop does), and ticking does not send a waiting one (Send does). The box is never disabled. The host handles the page's messages one at a time and holds them while a review's extraction and checks run, which can take minutes. A change made then shows on the page at once and is saved when the host is next free, in the order it was made, so a review started after the change uses the new value. If SOLIDWORKS closes in that window, the change is lost and the box reads the stored value next time.
- **The box changed after "Before this review" appears**: the review takes the box's value when it starts, which means at "Review available evidence" on that panel, at Review when nothing needs preparing, or at Retry. "No review tokens have been used." stays true on the panel.
- **Stop while a review waits**: Stop is not offered, because no turn runs. A stop request that reaches a waiting review anyway (a race, an older page) changes nothing: no event, no "stopped" turn, no model call, and Send stays offered.
- **Send with no usable credential, or a provider error at Send**: User Story 2, scenarios 4 and 5. The reason sits beside Send to model, never on the review's error card. Retry belongs to failed checks and is never offered for a failed send. Text that streamed before a failed first round stays in the Transcript as a failed attempt. A second Send resends the same first request once, and the opening is never carried twice.
- **Send failing before its first request** (the provider cannot be set up with the review's settings, or the record cannot be written before the request): no request is made and nothing is sent. The review keeps waiting, the reason is shown beside Send to model, and Send is offered again. The saved record does not change, because a send failure means a request was made; the event stream keeps the failure (default, added by the plan's second review).
- **A provider error after the model has answered at least once** (a model round completed): as today. The review finishes with what it has and the error card is shown.
- **A failed first request with the box ticked** (default, question 3): as today. The review ends with the error card and Retry. Its code results stay in its run folder, but its chat has failed: follow-ups are refused and it cannot be sent again, and Retry extracts again into a new folder.
- **The follow-up box while a review waits**: disabled, saying the review has not been sent to the model. A follow-up is a model request, and it would reach the model without the opening brief and digest. This applies only to a review started with the box unticked. A ticked review's follow-up box is today's, its failures included.
- **Question answers while a review waits**: User Story 3. The answers are applied by code and make no model request. An answered question cannot be answered again, as today. Send and a Settings save are refused while answers are being applied, and answers are refused while a Send is in flight or a re-run runs.
- **Accept, Reject or Defer while a review waits**: saved at once and kept at Send (User Story 3).
- **Settings save while a review waits**: allowed (decided 2026-10-08; refusing it would leave no way to enter the key Send needs). The waiting review falls back to the re-run of 61A (User Story 4). A save is refused while a turn runs, as today, and also while answers are being applied, a Send is in flight or a re-run runs, because each is work the restart would cut off partway.
- **The backend restarts while a waiting review is on screen**: the page's live link to that review is gone. The review moves at once to the restored state of User Story 4: the run-folder line shows, the size sentence has no number, and its next answer, decision or Send re-runs the checks first. Its next action is never refused as a review the backend does not know.
- **A re-run running**: it is new work as long as the checks themselves, less extraction and live detection. While it runs, whatever started it, a Settings save, Review, another review's chip, and the review's own answers, decisions and Send are refused as they are while a turn runs, and the status line says the saved evidence is being checked again. Stop is not offered, as it is not during today's checks.
- **A re-run that fails, is refused, or is cut off** (by a crash, SOLIDWORKS closing, or a shutdown): the earlier not-sent record stays the one the pane restores and FR-030 offers, with its questions, decisions and Send usable and its carried answers and decisions intact. The failed attempt is kept beside it in the run folder. The reason is shown in one line under the status line; Retry is not offered, because nothing needs extracting again, and the next answer, decision or Send tries the re-run again. Nothing is sent.
- **Live interference across a re-run**: the re-run does not detect again. It carries the first run's live-detection outcome from the earlier record: the same digest line, the same coverage row in the same bucket (a clean detection's checked item included), and, with SOLIDWORKS attached as it was then, the same tools withheld because of it. It never says SOLIDWORKS is not attached when the first run detected live. It judges the interference rows the first run merged into the folder's package, which are the rows the first run judged. One case cannot be carried whole: when the first run could not write its detected rows to the package, the re-run cannot judge them. It says so in one line, the interference family is unresolved, and decisions on findings of those rows are named as not applying. A first run whose live detection failed is carried as failed and is not retried; Review makes a fresh review.
- **Numbers that move across a re-run**: a re-run numbers its findings and questions afresh, and they can come out in a different order. A drawing read before the restart is the common case: the first run added that drawing's findings after the other checks' findings, while the re-run, with the drawing already in the package, checks it in its own place among the checks, and the drawing's candidate question is no longer asked. So a carried answer is matched to the question that asks the same thing (the same kind of question, the same parts and the same options), and a carried decision to the finding that says the same thing (the same check, the same parts, the same drawing places, the same entities among its inputs and the same configuration, so two findings on one pair of parts that differ only by the holes they judge stay apart). Neither is ever matched by its number alone. One that matches nothing, or more than one, is not carried and is named. The exception is a drawing answer whose drawing the earlier read already put in the package: its question is rightly not asked again, and the answer is carried as its outcome line, not named (FR-029).
- **The Standards profile changed by the Settings save that restarted the backend**: the re-run grades the saved evidence with the profile in effect, as Send uses the provider in effect (FR-016), and names the change in its one line of what was not carried, with any decision whose finding the new profile no longer raises (default, added by the plan's second review; put to the owner as plan question 3).
- **The backend crashes while a review waits**: the review was saved complete when the checks finished, so the crash loses nothing. Shown again, it is restored from its run folder with its questions, decisions and Send usable, each of which re-runs the checks first (User Story 4).
- **A crash or shutdown while answers are being applied**: the record keeps what was saved before the apply began. The answers being applied are lost and their questions show open again, nothing is sent, and no turn event is written. A crash after the regraded record was written leaves that record, with the answers answered. When a drawing read had already put its drawing into the run folder's package, the re-run checks that drawing in its place and does not ask its question again; its outcome line, never saved, is lost, and the re-run names that in its one line (a recorded limitation of FR-021).
- **An apply that fails while a review waits** (the drawing read or the regrade raising, or the record not being written): the same for the engineer as a crash during the apply. The review is shown from its run folder (the restored state of User Story 4) with the reason in one line, the answers being applied show open again (or answered, when the failure came after the regraded record was written; the re-run then carries them), no turn event is written and nothing is sent. Its next answer, decision or Send checks its saved evidence again first.
- **SOLIDWORKS closed while a review waits**: the run folder holds the complete checks-only review, and its report says it was not sent. On reopening, the reviewed document's newest review is offered if it was never sent or its send failed (default, question 2). A review whose checks failed is never offered; a not-sent review whose re-run failed is offered as its earlier record. An older not-sent review behind a newer review of the same document is not offered, though its report still says it was not sent. The review is matched to the document by its full path and configuration, never by file name alone. Its run-folder line names the date and time its checks ran, and its kept-review chip names the date whenever that is not today, so evidence from an earlier day never reads as today's. The search for it never delays opening the document: it runs off the SOLIDWORKS UI thread, narrows the run root's folders by name before reading any, and never reads a whole evidence package (FR-030).
- **Switching documents while a review waits**: the waiting review hides as any review does (feature 009), and Send is disabled with the other review actions. Returning to the document shows it again with Send offered. The live reads of SOLIDWORKS that a sent review makes behave as they do today for a review resumed after a switch.
- **The SOLIDWORKS model edited after the checks**: Send sends the review as it was checked, and nothing is re-extracted. A re-run after a restart reads SOLIDWORKS no further either (default). It carries the first run's live-detection outcome and judges the interference rows and the drawings that the first run merged into the run folder's package as they stand. The restored review's line names when its checks ran, so old evidence shows its age before Send. Pressing Review makes a fresh review of the edit. The pane does not detect the edit.
- **Retry**: the error card's Retry, offered when the checks themselves failed, re-prepares and re-extracts into a new folder as today and follows the box as it is when Retry is pressed. Nothing is sent when the checks fail, ticked or not.
- **Restoring a waiting review** (a page reload, choosing its kept-review chip, a restored folder): the snapshot says the review waits for Send. The page shows it waiting, never running, and opens no turn. A page reload while a re-run of it runs shows the review once the re-run ends, because the host answers the reloaded page only then. A live waiting review keeps its questions and decisions open. One restored from its folder keeps them usable through the re-run of User Story 4 (default, question 4), and feature 009's read-only sentence ("Follow-ups, decisions and answers are off.") is not shown for it.
- **The run folder of a not-sent review deleted or moved before a restored answer, decision or Send**: each is refused with feature 009's words ("This review can no longer be restored."), and nothing is sent.
- **Review pressed again while a review waits**: a new review starts as the box says. The waiting one is kept, marked as not sent on its chip, and can still be sent. There is no prompt and no dialog (no pane page uses one).
- **Several reviews waiting at once** (several documents, or Review pressed twice): each waits on its own, and Send sends only the review on screen.
- **Send pressed twice**: the second press is refused while the first is in flight, and nothing is sent twice.
- **The explanation pass**: it runs only after a turn that ended normally, which means only after Send or with the box ticked. It never runs for a review that was not sent.
- **A graceful shutdown while a review waits**: nothing changes. The record already says not sent, and no "stopped" or "error" turn is written.
- **The checks of an unticked review fail** (an unreadable package, an extraction error): today's error card and Retry. Nothing has been sent, and the record says so.
- **The checks re-run after a restart fail**: see "A re-run that fails, is refused, or is cut off" above. The earlier record stays the one the pane restores, not merely a file beside the failed one.
- **The report and saved record**: a not-sent review says "Not sent to the model" and names no model or provider as having run. A review sent after waiting says when it was sent. A failed send says when it failed and why. A review saved before this feature reads as sent, because all such reviews were.
- **The transcript**: a not-sent review's first line says it ran the code checks only. Send adds one line naming the provider and model that the review was sent to.
- **The replay and the recording reader** (feature 008): a review that was never sent is refused in one sentence, as having no model turn to replay. A review sent after waiting is also refused in one sentence (default). Its answers and events before Send would otherwise be read silently as an answer turn and a second session. Reviews sent at once are read as today.
- **The command-line review**: it stays as it is. It always sends, gains no flag, and its output line is unchanged (decided 2026-10-08: the owner asked for the pane; no test or parity check needs a flag; the chat server's own tests drive the checks-only path).

### Key Entities

- **Send setting**: the remembered value of the box, ticked or unticked, for the Windows user. It is a review-flow setting, not a lever.
- **Model status of a review**: one of three:
  - not sent: no request was ever made for it;
  - send failed: a request was made and no model round completed; the time and reason are kept;
  - sent: at least one model round completed. For a review that waited, the time Send was pressed, the estimate shown with its encoding, and the ids of the findings the opening named are kept.

  A review sent at once with the box ticked records nothing new, and a review saved before this feature is sent.
- **Waiting review**: a checks-only review that is complete on disk and can still be sent, whether held live by the backend or restored from its run folder. A restored one becomes live again at its first answer, decision or Send, through a code-only re-run. While that re-run runs, the review is being checked again and takes no action (FR-041). Until a re-run succeeds, the earlier record is the waiting review.
- **Earlier record**: what a not-sent review's run folder holds from before a restart. Beyond today's saved review, it holds what a re-run carries: the live-detection outcome, each drawing read's outcome line, and the answers and decisions made while the review waited. A re-run matches each answer to its question and each decision to its finding by what they say, never by number (FR-029).
- **First-request estimate**: the counted input tokens of the request Send would make next, counted with the one encoding for every provider and called approximate for Gemini. Otherwise it is "not counted", with the reason: no vocabulary on this machine, or a restored review not yet re-run.
- **Model's opening**: the first message of the model's first request, after the instructions and tools. In order: the package brief and pre-run digest as they stand at Send; then, only after answers given while the review waited, the wait's lines (one "Drawing {file}: {outcome}" line per drawing file read, then one line per answer saying code has applied it, with no instruction to re-run or continue and no line naming withdrawn findings); then the usual opening instruction.
