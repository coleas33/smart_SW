# Tools Added by Feature 004

All follow feature 001 `contracts/agent-tools.md` rules (ids and refs only, recorded steps, error
results never raise). Schemas are generated by `providers/schema.py`.

**What these tools are for.** The model proposes intent into the plan. It does not decide an
order, a move, a folder, a rollback, or a verdict, and it never touches SOLIDWORKS. That is
Principle II held exactly, and it is what lets stage 1's apply loop run with no model in it.

**Providers.** The remodel run reaches a provider through exactly one entry point,
`remodel/runner.py::build_provider`, through the existing provider layer: OpenAI (default) and
Gemini. Claude is not a provider in this product. `build_provider` refuses the scripted provider,
as it always has, and hands every other name to `cli.provider_factory`, the one body that
constructs an adapter for the review, the pane and the remodel run alike. It passes no efficiency
levers, so every lever stays off for a remodel run, as before. No other module of `remodel/`
reaches the registry or the factory.

*Amended 2026-09-23 (owner, decision 4A):* this paragraph used to say the remodel run
**constructs** a provider in exactly one place, `remodel/runner.py`, and `build_provider` did so
with its own copy of the construction body. Both copies carried the same wrong keyword, `redact=`
where `GeminiProvider` takes `secrets=`, so every Gemini remodel failed the same way every Gemini
review did and the fix had to land twice (`d47a91f`). One body builds both runs' adapters now;
`build_provider` stays the remodel run's one entry point and keeps the one decision that is the
remodel run's own, the refusal of the scripted provider.

## Registration condition

`tools/remodel_plan.py` is registered through one `Registration` in `tools/registry.py`, added
**only when `ToolContext.remodel` is set**, exactly the way `bridge_tools()` is added only when
the context carries a bridge. A review session, a general-chat session and the Model check tab
carry no `remodel` context, so none of these tools exists in any of them.

These tools are **not** query tools and **not** check tools. They are therefore not in
`MCP_TOOL_FUNCTIONS`, not in the MCP server, and not in `CliProfileWriter.EnabledTools`. Feature
003's test that the MCP function names and the terminal profile's `enabled_tools` are the same
list gains a sibling that asserts every tool on this page is in **neither** list, so a remodel
tool can never leak into the terminal or into MCP by accident.

## The tools

| Tool | Arguments | Writes | Returns |
|------|-----------|--------|---------|
| `propose_description` | `feature_id: str`, `text: str` | `plan.descriptions[]` or `plan.rejected_proposals[]` | `{feature_id, text}` or `{"error": ...}` |
| `propose_global` | `name: str`, `expression: str`, `rationale: str`, `evidence: list[str]` | `plan.globals[]` or `plan.rejected_proposals[]` | `{name, expression, evidence}` or `{"error": ...}` |
| `decide_fillet` | `feature_id: str`, `group: str`, `rationale: str` | `plan.targets[]` or `plan.rejected_proposals[]` | `{feature_id, group}` or `{"error": ...}` |
| `classify_unknown` | `feature_id: str`, `group: str`, `rationale: str` | `plan.targets[]` and `plan.deviations[]`, or `plan.rejected_proposals[]` | `{feature_id, group}` or `{"error": ...}` |
| `get_remodel_plan` | `section: str` | nothing | the named section of the current plan |

A rejected proposal returns `{"error": ...}`, which `RecordedTool.call` already turns into
`is_error=True` with no exception raised. That is the existing error path; this feature adds none.

**A rejection is also written down.** Before returning the error, the tool appends a
`RejectedProposal` (data-model.md section 1.9.1) to `plan.rejected_proposals[]`: the tool name, the
arguments the model sent, the rejection sentence, the id of the rule that refused it, and the
provider and model. FR-016 makes the plan carry the rejected proposals and US4 scenario 7 makes the
report list them with their reasons; a tool result alone is not persisted anywhere the report reads,
so returning the error and nothing else would leave both unsatisfiable. Every accepted proposal
likewise carries its `provider` and `model`, which is what FR-056 has the report print per
judgement item.

## Validation, inside the tool, before anything is written

Every rule below is a pure function over the plan and the package, has its own unit test, and is
enforced on the tool side rather than in the prompt. A prompt is guidance; this is the contract.

### `propose_description`

| Rule | Rejection |
|------|-----------|
| `feature_id` exists in the package | `unknown feature id` |
| the feature is **content** (not a folder, not an end tag, not reference geometry) | `not a content feature` |
| `1 <= len(text) <= 200` | `description must be 1 to 200 characters` |
| `text` contains no newline and no carriage return | `description must be a single line` |
| `text` is not equal, case-insensitively and trimmed, to the feature's `name` or its `type_name` | `description repeats the feature name` |
| the feature's current description is not `None` | `current description is unreadable; this feature is on the rebuild list` |
| at most one proposal per `feature_id` | `already proposed for this feature` |

The last-but-one rule is the one that matters most: `None` means unreadable and `""` means absent,
and writing over something unreadable is a silent edit with no recoverable inverse.

### `propose_global`

| Rule | Rejection |
|------|-----------|
| `name` matches `^[a-z][a-z0-9_]{1,31}$` | `global name must be lower_snake_case, 2 to 32 characters` |
| `name` is not already proposed in this plan | `already proposed` |
| `name` is not an existing global in the package | `a global with this name already exists` |
| `expression` parses over the declared globals and the documented function set | `expression does not parse` |
| every identifier in `expression` is a global declared earlier in the plan | `expression references an undeclared name` |
| `evidence` names only features that exist and are content | `evidence names an unknown feature` |
| every named feature carries, in the package, a numeric parameter that justifies the value | `no parameter data for this feature in the package` |
| `evidence` is non-empty unless every identifier in `expression` is a global declared earlier in this plan | `a literal global needs feature data behind it` |
| `rationale` is 1 to 300 characters | `rationale required` |
| no cycle is introduced among the proposed globals | `expression is circular` |

The documented function set is `sin cos tan atn arcsin sqr`, with **angles in degrees**, which is
what the equation engine reads. Numbers in an expression are in the **document's length unit**,
never metres: the executor seeds the literal from `GlobalEvidence.value_m`, which the package
carries in metres, converted to the document's unit, and one pure regression test asserts that a
120 mm value never produces `"w" = 0.12`. No `IDimension` member is read or written on this path;
`IDimension.set_Name` is not on the stage-1 allowlist at all.

**v1 scope note.** IR 1.2.0 carries `equations[]` but **not sketch dimensions**, so v1 can name and
repair globals that already exist and add globals justified from feature data (hole diameter,
shell thickness, fillet radius) and nothing more. Turning a hard-coded `50` in a sketch into
`plate_width` is out of scope and is a separate later feature that extracts dimensions into the
IR. A `propose_global` whose `evidence` names a feature that carries no such parameter in the
package is rejected with `no parameter data for this feature in the package`, never accepted and
silently dropped.

**`evidence` is evidence, not a dependency.** FR-030 forbids creating an equation that drives a
sketch dimension, and v1 renames no dimension, so nothing in the copy is rewired to a global this
run adds: the global names a value and drives nothing yet. The argument is called `evidence` and
not `drives` for exactly that reason, and the report says in those words that the added globals
drive nothing, so three new globals are never read as a parameterized part.

### `decide_fillet`

| Rule | Rejection |
|------|-----------|
| `feature_id` exists and classifies as a fillet | `not a fillet` |
| `group` is one of `3-Core`, `6-Quarantine` | `a fillet belongs in 3-Core or 6-Quarantine` |
| `6-Quarantine` only when the feature has no dependents | `this fillet has dependents; Quarantine requires none` |
| `rationale` is 1 to 300 characters | `rationale required` |

**Default and reporting.** A fillet the method calls ambiguous defaults to `3-Core`, which never
violates `rms.quarantine.has_no_children`, and every fillet decided this way is listed in
`report.md` as "reviewed as structural; move to Quarantine if cosmetic". The run is never blocked
on an evidence request, because the run is non-interactive by design.

### `classify_unknown`

| Rule | Rejection |
|------|-----------|
| `feature_id` exists and classifies as `unknown` or `ambiguous` | `this feature already has a class` |
| `group` is one of the six RMS group names | `group must be one of the six` |
| `rationale` is 1 to 300 characters | `rationale required` |

Every accepted call also appends to `plan.deviations[]`, so the report can state that a group
assignment came from the model rather than from the type table. A feature the model does not
classify stays `unclassified` on the rebuild list; it is never treated as movable, per Principle I.

### `get_remodel_plan`

`section` is one of `summary`, `targets`, `order`, `pins`, `rebuild`, `folders`,
`descriptions`, `globals`, `deviations`, `rejected_proposals`. Any other value returns `{"error": "unknown section"}`.
The tool is a read-back so the model can see what its own proposals became after validation; it
never returns the package, the change log, or anything from the run folder outside `plan.json`.

## What is deliberately absent

No tool proposes a reorder, a folder, a rename, a rebuild, a save, a rollback, a discard, or a
geometry verdict. No tool names a document, a path, or a run folder. No tool can cause a write to
SOLIDWORKS: the `remodel.*` bridge commands are commands, not tools, and the remodel bridge secret
is never handed to the tool layer. One test asserts that the union of the argument names of every
tool on this page contains no `path`, `document`, `document_id`, `run_dir` or `persist_ref`.
