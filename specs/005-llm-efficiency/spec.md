# Feature Specification: LLM Efficiency, Speed, and Token Usage

**Feature Branch**: `005-llm-efficiency`

**Created**: 2026-09-16

**Status**: Draft (revision 1, written from `docs/llm-efficiency-options.md` and the design brief of 2026-09-16)

**Input**: `docs/llm-efficiency-options.md` (the measured baseline, twelve levers in three tiers, the evaluation protocol, and the proposed phases), plus the owner's governing rule recorded on 2026-09-16: "instrument first, then one lever at a time behind a flag, default off, adopted only on measured evidence with no quality regression. I do not want everything implemented without testing the trade-offs." Every technical claim below comes from the design brief of 2026-09-16, which is the authority for what is VERIFIED and what is UNVERIFIED. **VERIFIED** means read in this tree, or read in a package installed under `reviewer/.venv/Lib/site-packages` (`openai` 3.13.0, `google-genai` 2.23.0), at the file and line cited, on 2026-09-16, or produced by a script run against this tree; it never means an API was observed behaving a certain way. **UNVERIFIED** means the claim needs a live provider call, a SOLIDWORKS seat, or a timed run, and every UNVERIFIED claim that gates a decision carries the probe id that settles it. The reviewer stays read-only. The providers are OpenAI (default) and Gemini through `agent/providers`; no part of this feature uses Claude.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Every Run Reports What It Cost (Priority: P1)

An engineer runs a review and can afterwards say what it cost, in numbers the provider itself reported. Each model round trip records its input tokens, its cached input tokens, its output tokens, its reasoning or thoughts tokens, its total, and its latency, as the provider names them. The session sums them under a rule that never invents a number: a total over rounds where any round did not report a field is reported as unknown, not as a partial sum, and a field the endpoint omitted is unknown, not zero. The pane shows the running cost of the turn, `report.md` gains a tokens section, and the benchmark scorecard carries tokens, cached share, round trips, wall clock, and seconds to the first finding. The first deliverable of the whole feature is a baseline table with a row for each provider and model, produced by running the benchmark set, because no token number and no agent review result exists for any package today.

**Why this priority**: nothing else in this feature is decidable without it. Today no token or cost number exists for any run (VERIFIED: `grep -rn "usage" reviewer/src/swreview/agent/providers/*.py` returns nothing, and `TurnResult` carries `reason`, `text`, `steps`, `messages` and no usage, `agent/providers/__init__.py:187-199`). Every lever below is adopted or rejected against a recorded number, and until this lands there are no numbers to adopt against. This user story has **no flag**, because recording what a run cost is not an experiment.

**Independent Test**: run a review against the fake provider with no network and no key, and read `session.json`: it carries per-round usage, a session total, and the round-trip count, and the totals equal the fake's scripted numbers exactly. Then run `swreview review` on `cover-blind-tap` against OpenAI and against Gemini and read the same fields filled with real provider numbers, and score both runs into a scorecard whose new columns are populated. That pair of runs **is** the baseline row that does not exist today.

**Acceptance Scenarios**:

1. **Given** a turn in which the model makes six serial tool calls, **When** the turn ends, **Then** seven round trips are recorded, one per provider request, each with its own usage and latency, and the round count is a number distinct from the tool-call count.
2. **Given** an OpenAI response whose input-token details omit the cache-write count, **When** usage is recorded, **Then** that field is unknown and is never recorded as `0`. (VERIFIED: the SDK builds response models with `BaseModel.construct`, `openai/_models.py:231-259`, so a field the server omitted takes the field default, which for a required field is `None`; reproduced against the installed package.)
3. **Given** a session in which one round reported no output-token count, **When** the session total is computed, **Then** the output total is unknown rather than the sum of the rounds that did report, and the report says unknown.
4. **Given** a turn that raises on its third round after two paid rounds, **When** the run finalizes and re-raises, **Then** the two paid rounds are already on disk in the event stream and are in the session total, because usage is recorded per round as it happens and is not carried home on the turn result.
5. **Given** a Gemini streamed turn whose final chunk carries usage metadata and no candidates, **When** the stream is consumed, **Then** that usage is recorded, not dropped.
6. **Given** a Gemini run, **When** the numbers are reported, **Then** the tokens in the cached content are understood as already inside the prompt token count and are not added to it, and the tokens from tool results are understood as outside the prompt token count and are added to the total. (VERIFIED from the installed package's own field descriptions, `google/genai/types.py:8445-8496`.)
7. **Given** a run on each provider, **When** the two are compared in the ledger, **Then** the comparison is made on total tokens only, and any per-provider field is reported under the provider's own name, because OpenAI's reasoning tokens are a subset of its output tokens while Gemini's thoughts tokens are a separate addend of its total.
8. **Given** a feature 001 session written before this feature, **When** it is loaded, scored, and rendered, **Then** it loads and validates, the scorecard reports its token columns as unknown without raising, and its `report.md` is byte-identical to the current golden.
9. **Given** any run, **When** the pane is watched, **Then** the tokens spent so far, the cached share, the round trips, and the latency of the last round are visible while the turn is still running, from the same stream the pane already reads.
10. **Given** the same scripted fake review run twice, **When** the two sessions are compared, **Then** the recorded usage is identical, because the fake emits a fixed synthetic record and nothing in the fake is random.

### User Story 2 - The Lever Harness: One Flag Each, Default Off, Measured Before Adopted (Priority: P2)

Every efficiency lever in this feature is a single named setting on one settings object, defaulting to off, recorded in `session.json` so a result can be attributed to a configuration. To evaluate one, an engineer runs the benchmark set six times, alternating off and on, three of each, at one commit with one provider, one model, one effort, and byte-identical packages; scores each run; and then runs one compare command that reads the resulting scorecards and renders the results ledger. The ledger is a rendering of `scorecard.json` files, never a hand-typed table. Each row carries the commit, the lever, the arm, the repetition, the provider and model, the other levers that were on, the token and round-trip and wall-clock numbers, the quality numbers, and the lever's own specific counter. The decision column is `adopt`, `keep off`, or `re-measure`, and a lever that fails keeps its row.

**Why this priority**: this is the owner's rule turned into machinery. Without the recorded settings there is no attribution; without the alternated repetitions there is no defence against provider-side drift; without the rendered ledger the numbers go stale and cannot be audited. It is second only because it needs the measurement layer's numbers to have anything to record.

**Independent Test**: with the fake provider and no network, run the benchmark set with a lever off and with the same lever on, score both, and run the compare command: two rows appear, differing only in the arm and in the recorded settings, each naming the commit and the other levers that were on. Then take three off-scorecards and three on-scorecards for one real lever and confirm the decision row reports the median, the minimum, and the maximum of each metric, the worst-case defect loss, and a decision derived by the stated rule rather than typed by a person.

**Acceptance Scenarios**:

1. **Given** a run with no lever requested, **When** the session is written, **Then** every lever is recorded as off, and the run behaves identically to a run of the tree before this feature.
2. **Given** a run with one lever requested on the command line, **When** the session is written, **Then** the full set of lever values is recorded on the session, so the results row can be rebuilt from the run folder alone.
3. **Given** a lever being measured, **When** an engineer looks in the pane's settings, **Then** no lever checkbox is there, because an engineer toggling an experiment flag mid-pilot makes the pilot's own numbers unreadable; an adopted lever becomes a default in code, not a checkbox.
4. **Given** six run folders for one lever, three off and three on, **When** compare runs, **Then** it renders one raw row per run and one decision row per lever, provider, and model, and every column has exactly one source, with no number computed in two places.
5. **Given** a lever whose three off-runs disagree with each other about which known defects were found, **When** the decision is computed, **Then** the decision is `re-measure` with the disagreement named, because a gate whose control arm is unstable cannot decide anything.
6. **Given** a lever whose on-arm misses, in any one of its three runs, a known defect that any one off-run found, **When** the decision is computed, **Then** the decision is `keep off`, on the worst case rather than on the median.
7. **Given** a lever whose median total-token reduction and median wall-clock reduction are both under 20 percent, **When** the decision is computed, **Then** the decision is `keep off`, because a saving inside run-to-run variance at three repetitions does not justify a flag, a settings field, a test suite, and a permanent branch in the code.
8. **Given** the benchmark set as it stands today, **When** any Tier 2 or Tier 3 gate is attempted, **Then** the harness reports that the set is too small to gate on and names why, rather than producing a decision. (VERIFIED: `benchmarks/sets/pilot.json` holds one package, `cover-blind-tap`, not held out, whose answer key has two known defects and whose package has zero mates, holes, threads, fasteners, faces, bodies, interferences, captures, features, and equations; recall is `None` whenever the held-out defect count is zero, `benchmark/scorecard.py:200-204`.)
9. **Given** two levers measured in the same arm, **When** the row is rendered, **Then** the other levers that were on are named in the row, because the levers interact and a number without that column is unattributable.

### User Story 3 - Tier 1: Payload and Caching, Measured One at a Time (Priority: P3)

Three levers reduce what is sent on every request without changing what the reviewer does. **Lever 3 (prompt caching)** names the cache with the session id so a hit survives the backend restart the pane performs on a settings save, and records the provider's own cache diagnostics so a miss comes with a reason rather than a guess. **Lever 2 (trim tool descriptions)** moves the policy and call-protocol halves of the long tool docstrings out of the per-request tool array and into the system prompt, keeping the text in exactly one place. **Lever 4 (tiered tool exposure)** withholds the resilient-modeling tools from a package that carries no feature rows, and a model that asks for a withheld tool is told why, with the checklist item closing as unresolved carrying that sentence, never as a silent miss. They are measured in the order 3, then 2, then 4, because lever 3's diagnostics are the instrument that prices the other two.

**Why this priority**: it is the largest recurring cost with the smallest behavioural risk. 34,065 bytes of tool schemas go out on every request today (VERIFIED, measured on this tree: 32 tools with no bridge, 34,065 bytes as OpenAI tools, 34,248 as Gemini function declarations, 37,709 with the three bridge tools), roughly 8,500 tokens per request (UNVERIFIED as a token count until the measurement layer runs), and a review with 60 tool calls spends that 60 times.

**Independent Test**: measure the encoded tool payload with a lever off and on with no provider and no network: the byte counts and the tool counts are exact and deterministic, and the test runs in continuous integration. Then run the six-run protocol per lever per provider and read the cached share, the total tokens, the tool-name histogram, and the scorecard.

**Acceptance Scenarios**:

1. **Given** a session that restarts its backend process mid-review, **When** the next request is made, **Then** the cache key is the same as before the restart, because it is the persisted session id and not a process-local value.
2. **Given** a request that missed the cache, **When** the miss is recorded, **Then** the provider's own reason is recorded alongside the count of tokens that missed, rather than a guess about which part of the prefix changed. (VERIFIED: the prompt-cache diagnostics object, `openai/types/responses/response.py:195-241`, reached through the response field `prompt_cache_diagnostics` at `:418`, is a discriminated union of hit, miss, comparison-not-found, and unavailable, whose miss member carries `cache_missed_tokens` and a nine-member reason enum at `:202-212` including a tools-changed, a cache-key-changed, and an input-changed member, requested by naming a comparison response id. UNVERIFIED that our seat accepts it on our default model, probe L3b.)
3. **Given** any session, **When** the prefix is examined across the turns of that session, **Then** the system prompt and the tool list are byte-identical from the first request to the last, and a regression test fails if a change makes them vary.
4. **Given** lever 2 applied, **When** the tool array and the system prompt are rendered, **Then** each moved note appears exactly once, in the system prompt, and the text still lives in exactly one docstring, so a note that goes stale goes stale in one place.
5. **Given** lever 2 applied, **When** a tool description is read, **Then** it is a whole first paragraph a person wrote, never a run-time truncation that ends mid-word, and a description over the stated cap fails the build rather than being cut at run time.
6. **Given** lever 2 measured, **When** the result row is read, **Then** it names which other levers were on, because moving text into the system prompt moves it into the cacheable prefix and lever 3 will already have captured part of that saving on the second and later requests of a turn.
7. **Given** a package that carries no feature rows and lever 4 on, **When** the turn starts, **Then** the resilient-modeling tools are absent from the tool array, the saving is 8,093 bytes or 23.8 percent of the payload (VERIFIED, measured on this tree), and the tool list does not change again for the rest of the session.
8. **Given** that same run, **When** the model asks for a withheld tool anyway, **Then** the call still produces a tool-started and tool-finished pair, the result names the rule that withheld it, the checklist item closes as **unresolved** with a sentence an engineer can read, and the failed-tool bucket stays empty.
9. **Given** a model that calls a tool name that never existed, **When** the call is dispatched, **Then** it is still recorded as a failed tool call, because a hallucinated name and a withheld tool are different facts.
10. **Given** lever 4 measured, **When** the result row is read, **Then** it states the asymmetry, 24 percent on a model-check package and 0 percent on a full assembly package, rather than averaging the two into one number that describes neither.

### User Story 4 - Tier 2: Changing How the Review Runs, Gated by the Scorecard (Priority: P4)

Three levers change the shape of the review loop. **Lever 5 (pre-run deterministic checks)** runs, before the first turn, the four check families that already enumerate themselves without a model, and hands the model a digest of the results together with a block naming what was **not** evaluated and why. **Lever 6 (parallel tool calls)** allows the model to request several tool calls in one round trip on OpenAI; the calls are still executed locally one at a time in request order. **Lever 7 (coverage-driven stop)** ends a turn once every checklist item is genuinely closed and no evidence request is open, by withdrawing the tools for the next round rather than by cutting the turn off mid-call. Each is measured alone, and levers 5 and 7 are never measured in the same arm until each has been gated on its own.

**Why this priority**: the largest expected savings and the largest behavioural risk sit together here. A pre-run digest that makes the model stop exploring, a batching request that makes the model call checks it would have skipped, and a stop rule that rewards a model for marking items skipped are all failures the token number would report as wins. Each ships with the counter that catches its own failure.

**Independent Test**: for lever 5, run a package through the pre-run with no provider and compare the resulting session against a model-driven run of the same checks on the runner's own verdict key: the verdicts match, which is the strongest available statement that the pre-run is the same checks and not a second implementation. For lever 6, script a single response carrying three tool calls and assert three ordered steps, three tool outputs, and a still-valid history. For lever 7, unit test the stop predicate over hand-built sessions with no provider, then assert on a recorded client that a stopped session can still answer an evidence request afterwards.

**Acceptance Scenarios**:

1. **Given** lever 5 on, **When** the pre-run executes, **Then** it calls the same tool functions through the same dispatch the model uses, producing real steps, real findings, real coverage, and real events, so the report is structurally indistinguishable from a model-driven run and every finding still cites a real step.
2. **Given** the pre-run digest, **When** it is placed, **Then** it is in the first user message and not in the system prompt, because the system prompt is the cacheable prefix and the digest is per package.
3. **Given** the pre-run digest, **When** it is read, **Then** it names what was not evaluated and why, and each of those lines corresponds to a skipped coverage item written at the same moment, so the report says the same thing the model was told.
4. **Given** lever 5 measured, **When** the result row is read, **Then** it carries the per-run call counts of the two checks that are never pre-run, and a fall in those counts fails the lever regardless of the token saving, because it means the digest suppressed exploration.
5. **Given** lever 6 on and a response carrying three calls, **When** the calls are executed, **Then** they run one at a time in request order, each gets its own output appended to the history, the step log stays deterministic, and no tool runs on another thread.
6. **Given** lever 6 on and a step budget smaller than the calls requested, **When** the budget runs out mid-round, **Then** the over-budget calls receive the budget-exhausted output so the echoed history stays valid, and the turn ends on the budget.
7. **Given** lever 6 measured, **When** the result row is read, **Then** it carries both round trips and tool calls, because a model asked to batch may call checks it would otherwise have skipped, which shows as steps rising while round trips fall.
8. **Given** lever 6 on Gemini, **When** the result row is read, **Then** it states that Gemini already makes parallel tool calls in production and that this lever is not measurable as an A/B there, rather than presenting a fabricated comparison. (VERIFIED: the OpenAI adapter sends parallel tool calls disabled on every request, `openai_provider.py:308`; the Gemini adapter sets no such option and its loop is already written for several calls per round, `gemini_provider.py:334-357,444-466`; and the installed package offers no option to disable it.)
9. **Given** lever 7 on and every checklist item closed by a finding or by an explicit check, **When** the next round is requested, **Then** the model is offered no tools for that round, writes its closing message, and the turn ends through the normal path with every tool call having its output, so the session can still be continued or have an evidence request answered afterwards.
10. **Given** lever 7 on and items closed only by being marked skipped or out of scope, **When** the stop predicate is evaluated, **Then** it does not fire, because skipping six of nine items is giving up rather than finishing, and the predicate deliberately differs from the finalization rule for that reason.
11. **Given** lever 7 measured, **When** the result row is read, **Then** it carries the closing bucket mix and how often the stop fired, because a lever that fires on one package in five is not the same lever as one that fires on five in five and the token average hides that.
12. **Given** levers 6 and 7 both on, **When** the round that closes the last checklist item also carries three more calls, **Then** those three still run, because the stop withdraws the tools for the **next** round; this is intended and is stated so the measured saving is not read as a defect.

### User Story 5 - Tier 3: Extraction and Re-review, on the Workstation (Priority: P5)

Three levers attack the cost that is paid before and around the model. **Lever 9 (package reuse)** lets an unchanged design skip extraction, keyed on a content key honest enough to detect a change, and refuses reuse wherever the key cannot see one. **Lever 10a (lazy meshes)** lets a dump skip mesh export and have a check fetch a body's mesh through the bridge when it needs one, and say unresolved when it cannot. **Lever 11a (carry over resilient-modeling findings)** carries a previous run's findings for the one check family whose entire input is already covered by an existing fingerprint, and never silently. **Lever 12 (rules over tokens)** is not a flag at all: every finding class the model keeps producing that a rule can express becomes a deterministic check, which costs zero tokens per part thereafter.

**Why this priority**: these three are the only levers that touch the extractor, the bridge protocol, and the intermediate-representation schema, and they are invisible to the benchmark runner (VERIFIED: the benchmark iterates pre-built package directories and performs no dump, `benchmark/runner.py:88-104`), so each needs a workstation harness and a pass-fail precondition of its own before the scorecard is consulted at all.

**Independent Test**: for lever 9, dump an unchanged document twice, once cold and once reusing, and assert the reused package is byte-identical to a fresh dump apart from the identifiers and timestamps that are legitimately new; that assertion is the gate, ahead of any timing. For lever 10a, review the same design with meshes exported and with meshes fetched lazily and assert the tool-envelope check reports the same bodies swept and the same hits, or reports unresolved naming what it could not fetch. For lever 11a, review a design, edit one part, re-dump, and review again: every finding touching the edited part is re-run and not carried.

**Acceptance Scenarios**:

1. **Given** a design whose referenced part was edited outside the assembly, **When** reuse is considered, **Then** the key differs and the package is extracted again, because every referenced document is in the key and not only the root.
2. **Given** a document with unsaved in-memory changes, **When** reuse is considered, **Then** reuse is refused and the refusal says why, because a file modification time does not move until a save.
3. **Given** a package written by a dump that skipped a phase, **When** reuse is considered, **Then** reuse is refused, because a partial dump is written with gaps and nothing in it says the dump aborted.
4. **Given** a model-check package and a request for a full review, **When** reuse is considered, **Then** the key differs and the package is extracted again, because a model-check package carries empty holes, fasteners, faces, and bodies by design and reusing it would silently narrow the review.
5. **Given** a reuse that does happen, **When** the engineer reads the pane, the report, and the session, **Then** all three say the extraction was reused, naming the run it came from and its age, so reuse is never silent.
6. **Given** lever 10a and a check that needs a body's mesh, **When** the bridge is available, **Then** the mesh is produced by the same tessellation path the dump uses, so an answer never depends on how the mesh arrived.
7. **Given** lever 10a and no bridge, **When** the tool-envelope check runs against a body it cannot fetch, **Then** the result is unresolved naming the body, never a clean result over zero bodies.
8. **Given** any run at all, including today's, **When** the tool-envelope check sweeps zero bodies, **Then** it reports unresolved with the reason and never reports a clean check; this defect is reachable today and is fixed first, on its own, before lever 10a is written.
9. **Given** lever 11a, **When** a finding is carried over, **Then** the finding records which session it came from, when, and the key that justified it, the coverage entry says it was carried over, and the report states how many findings were carried against how many were re-run.
10. **Given** a finding that is suspected or unresolved, or that carries an engineer's disposition, or that came from a run cut short by the step budget, **When** carry-over is considered, **Then** it is re-run, because those are exactly the verdicts that should not be frozen.
11. **Given** lever 11a measured, **When** the result row is read, **Then** it carries the count of carried findings per arm, because a lever that improves recall by remembering is not an improvement.
12. **Given** a finding class the model keeps producing that a rule can express, **When** the standing review of findings by check kind happens, **Then** it is proposed as a deterministic check, and the measurement is the count of findings by check kind over time, which the instrumented scorecard reports for free.

### Edge Cases

**Measurement**

- A provider reports no usage object at all for a round: the round is recorded with every field unknown and a latency, and the session total for every field becomes unknown. The run is not failed and nothing is estimated.
- A field the endpoint omits, for example the cache-write count on a model that does not report it: unknown, never zero (VERIFIED reproduction against the installed package; the reason is that the SDK constructs response models field by field from what the server actually sent).
- A Gemini stream whose chunk usage is a delta rather than a running total: the adapter takes the last chunk that carried usage, which is correct if the values are cumulative and correct if only the final chunk carries them, and wrong only if they are deltas. That case is UNVERIFIED and is probe G3; until it is answered the recorded number carries that caveat.
- A turn that raises after paid rounds: the paid rounds are already on disk, because each round's usage is appended to the event stream as it happens and the stream is opened, appended, and closed per event precisely so it survives the process dying.
- The benchmark runner and the session finalizer both write the unattended-runtime field, and the benchmark's value wins because it runs last and includes package load and adapter construction (VERIFIED). The baseline table states which of the two it is quoting rather than leaving a reader to guess.
- A session from feature 001 or 002 with no usage at all: loads, validates, scores with unknowns, and renders a report byte-identical to its golden.
- The static baseline table in the input document disagrees with the tree: it already does, and by enough to matter (29 tools and 32,435 bytes recorded against 32 tools and 34,065 bytes measured). The table is regenerated from the tree by a committed test, and the input document is corrected in the same change, rather than transcribed again.

**Cache misses**

- The pane saves settings mid-review and the backend process restarts: the cache key is the persisted session id, so the prefix is still named the same and the hit survives. A process-local key would look identical and would silently drop every hit, which is exactly why the miss reason is recorded.
- The effort level changes between turns: the provider reports the miss with a reason naming the effort change. The pane refuses a settings save during a turn but not between turns, so this is a real path.
- Anything per-turn is placed in the system prompt, for example a coverage digest, the open checklist items, or a timestamp: the prefix is invalidated for the rest of the session. This is the reason lever 5's digest goes into the first user message.
- Lever 4 changes the tool list mid-session: the provider reports a tools-changed miss with the count of tokens that missed. The design forbids that by making tier selection package-decidable and fixed for the session, and the test asserts no mid-session tools-changed miss appears.
- Toggling parallel tool calls does not appear in the provider's miss-reason enum, so it should not break the prefix. UNVERIFIED, probe L5, and only relevant once lever 6 is taken up.
- The comparison option that produces the diagnostics is rejected by our seat: the diagnostics half of lever 3 is off the table, and the spec says so rather than assuming it works (probe L3b).
- A Gemini run already shows healthy implicit cache hits with no explicit cache: then the explicit cache lifecycle is **not written at all**, and that is a result, not a shortfall (probe G4).
- A Gemini request that names a cached content while also sending the system instruction and the tools: rejected by the service with an error that kills the whole review rather than degrading it, and the installed package performs no validation that would catch it (VERIFIED by absence). One function builds both request shapes from one nullable cache name, tested both ways.
- A crashed process leaves a Gemini explicit cache entry behind: the time to live is bounded so the leak is cheap and self-healing, rather than a standing bill nobody sees.
- Our prefix turns out to be hitting the implicit cache already: then lever 3 on OpenAI has a token column close to flat by design, and its row **computes `keep off`** by the FR-028 rule like every other row. That is a result, and the row says so. The observability case for the diagnostics and the stable key is recorded in `decision_reason` beside the computed value and signed in `owner_signed_off`; it is not a second route to `adopt`, because probe L2's answer is in `probe-log.md` and not in any scorecard (FR-024, FR-027). If the owner wants such a lever adopted without meeting the threshold, that is an amendment to FR-027 and FR-028 argued in writing, not an exception granted here.

**A withheld tool the model needed**

- The model asks for a tool the tier withheld: it is answered, not ignored. The tool is registered but not offered, the dispatch resolves it, the result names the rule, and the checklist item closes as unresolved with that sentence.
- The same call today, without this design, writes a **failed** coverage entry, which says the tool broke when in fact we declined to offer it, is excluded from the buckets that close a checklist item, and hands the model a list of every tool name inside an error string. All three are wrong and the design changes all three.
- A tier withholds tools for a package that genuinely cannot be graded for that family: one function decides "this package cannot be graded for this family, and here is the sentence saying why", and both the withheld-tool result and the pre-run digest say the same sentence. One reason, one writer.
- The unresolved count rises because tools were withheld: the count is read as two numbers, unresolved-because-withheld and unresolved-for-any-other-reason. The first rising and the second flat is the lever behaving as designed; the second rising fails it.
- A tier withholds a tool the package could in fact have supported: that is a defect in the tier rule, not an acceptable trade, and it shows as unresolved-because-withheld on a package whose feature rows are not empty. The rule reuses the condition the existing resilient-modeling endpoint already refuses on, so there is one rule rather than two that can disagree.

**A stale package**

- The key as the input document proposes it, built from path, version, and modification time from the manifest, reduces today to path and configuration, because the manifest carries no content hash, no file size, and a modification time that is hardcoded null with a gap on every document of every dump (VERIFIED, `Dump/ManifestBuilder.cs:57,92-98`). Reusing on that makes the stale-package failure certain rather than possible, so the key needs new fields or the lever is dropped.
- A suppressed or lightweight component later resolved: no file changes, but what the review can see does change, so each component's suppression state is in the key.
- A dump that continued past a failed phase: the package is written either way with gaps and nothing in it says the dump aborted (VERIFIED, `Dump/PackageWriter.cs:38-41,142-235`), so reuse refuses any package carrying a phase-level tool error.
- Clock skew between machines: produces a false miss and a redundant extraction, which is the safe direction.
- The index of previous run folders is missing or unparseable: that means no reuse, never an error.
- The referenced run folder or its package has been deleted since the index was written: verified before reuse, and a missing folder means extract again.
- The key is recomputed at reuse time from the live document's references, never trusted from the file, because the file is the thing whose freshness is in question.
- A package identifier is freshly generated on every dump today (VERIFIED, `Dump/PackageWriter.cs:136`), so it cannot be a reuse key and is one of the fields the byte-identity gate must exclude.

**A carried-over finding**

- A finding is carried whose check reads an input the fingerprint does not cover: this is the failure that makes a carried finding a lie, so version 1 carries **only** the one check family whose entire input is inside an existing fingerprint, and excludes the one rule of that family that reads an array the fingerprint does not include.
- A finding carried from a run that ended on the step budget: refused. A verdict from a run cut short is not a verdict to reuse.
- A finding the engineer accepted, rejected, or deferred: refused. Carrying it without the human decision is worse than re-running; carrying it with the decision has the reviewer re-assert a human's judgement.
- An accepted exception touching the same components moved to needs-review: refused.
- A finding carried for twenty consecutive runs: refused by an explicit cap in age or in runs, because a finding carried twenty times has not been computed for twenty runs.
- A carried finding changes the finding's status: forbidden. Carry-over is provenance, not status; a carried demonstrated finding is still demonstrated, and overloading the status field would break the scorecard's matching rules.
- Carry-over raises recall: reported with the carried count beside it, so a reader can see whether the quality came from computation or from memory.
- A component the previous run cited is not in the new package: the existing fingerprint path raises rather than silently re-binding to another component, and the finding is re-run.

**A fast model routing mistake**

- Lever 8, a fast model for some jobs and the large model for others, is **deferred out of this feature**, and the routing mistake is the reason that deferral is stated here rather than left implicit. Of the four jobs the input document names, the Ask tab is not ours to route at all: it is the embedded terminal running the engineer's own command-line assistant against our tool server, and that assistant chooses its model. Tool-result summarisation does not exist today; what exists is a fixed-length truncation with no model in it (VERIFIED, `agent/providers/__init__.py:270-283`), so building it is a new feature whose own failure, a summary that drops the number a check needed, is a quality regression no scorecard would attribute to the summariser. That leaves one mechanical job on a minority of turns.
- The mistake that would matter if it were built: the fast model, asked to re-run a finding, records a **new** finding instead of replacing the old one, and the report then carries two contradictory verdicts on the same condition. If lever 8 is ever taken up, that reconciliation is the test that matters.
- The accounting mistake that comes with it: two models in one session breaks the invariant that the session names one model, and tokens from two tiers are not comparable, so the measurement would have to be in money and the scorecard would need a price table. Five modules and two contracts for a saving on a minority of turns is the reason for the deferral, and it is a scope judgement, not a measured result.
- What this feature does for the Ask tab instead: make its tool payload smaller, which is levers 2 and 4, and say so rather than listing the Ask tab as a lever 8 deliverable it cannot be.

**The harness and the gate**

- A lever's on-arm and off-arm are not reachable by flipping a boolean, because the change was a rewrite rather than a switch: the A/B would run against two commits and the results row would carry both (FR-032). **This feature has no such lever.** Lever 2 is not one: its flag-off path hands over the rejoined description, byte-equal to the pre-split text, so both arms run from one commit (FR-033, FR-039, SC-007). The guard stays because it is cheap with zero instances; what does not stay is an exception to the compare command's same-commit refusal.
- A lever is invisible to the benchmark runner (levers 9 and 10a): it is gated by its own pass-fail precondition on the workstation and by a dump-timing measurement, and its row says the scorecard was not the gate.
- Two levers are measured together by accident: the other-levers-on column exists so the row is still attributable, and the interaction table names the pairs whose results must not be read as independent.
- A lever's numbers come out flat: the row stays in the ledger with a decision of `keep off`. Nothing is removed from the ledger for being unflattering.
- A lever passes on one provider and fails on the other: both rows stand, the decision is per provider and model, and no lever is adopted for a provider it was not measured on.

**The lever harness and the results ledger (User Story 2)**

- **FR-018**: Every lever in this feature MUST be one named boolean field on **one** frozen settings object, and every field MUST default to off. A lever MUST NOT introduce its own settings object, its own session field, or its own scorecard grouping.
- **FR-019**: That settings object MUST be threaded as a single argument through the review entry point, the benchmark runner, and the command-line review path, and MUST NOT become one plumbed parameter per lever.
- **FR-020**: The session record MUST carry the full set of lever values for the run, as an optional field so a session written before this feature is still valid. Without it no results row can be attributed to a configuration and the results table cannot be rebuilt from the run folder.
- **FR-021**: No lever MUST appear as a setting in the pane while it is being measured. A lever is selected on the command line for a benchmark run; an adopted lever becomes a default in code, not a checkbox.
- **FR-022**: The A/B procedure for one lever, one provider, and one model MUST be six runs, three off and three on, alternated off, on, off, on, off, on, so provider-side drift during the session does not land entirely on one arm. Fixed across all six: the benchmark set file, the answer keys, the model, the effort, the step budget, the checklist, the packages on disk byte for byte, and the tree at one commit. Recorded per run: the commit, the lever values, the provider, the model, the effort, and the start time.
- **FR-023**: The three repetitions of an arm MUST be three separate runs into three run folders, aggregated by a compare command that reads N scorecards. A repetition loop inside the benchmark runner MUST NOT be built: it would have to invent a nested folder layout and an aggregation that is the scorecard's job, and separate folders make re-running one flaky package possible.
- **FR-024**: `swreview benchmark compare` MUST render the results ledger from scorecard files, never from hand-typed numbers, in two tables: a raw row per run and a decision row per lever, provider, and model. Every column MUST have exactly one source and no number may be computed in two places.
- **FR-025**: The raw row MUST carry the run, the commit, the lever, the arm, the repetition, the provider, the model, the effort, the package, the token fields as recorded, the round trips, the tool calls, the cached share, the wall clock, the seconds to the first finding, the valid findings, the missed known defects, the false alarms, the unresolved count, and the coverage bucket mix.
- **FR-026**: The decision row MUST carry the reps, the other levers that were on, each metric as median with minimum and maximum off and on, the quality metrics off and on, the recall on held-out packages off and on, the worst-case defect loss, the lever's own specific counter, the decision, and a link to the run directories.
- **FR-027**: The decision MUST be exactly one of `adopt`, `keep off`, or `re-measure`, and MUST be derived by the rule in FR-028 rather than typed by a person. The enum is closed at three: an unstable control arm is `re-measure` with `CONTROL UNSTABLE` as its printed reason, never a fourth value. The owner's approval MUST be recorded as a separate field beside the computed one, `owner_signed_off` with a date, which the compare command never writes and which no flag default may change without. A lever that fails MUST keep its row with its numbers; no row is removed for being unflattering.
- **FR-028**: The adoption rule MUST be: **no known defect lost, taken on the worst case** (rejected if any on-run misses a defect any off-run found), **no new false alarm, taken on the median with the worst case recorded**, and **a median reduction of at least 20 percent in total tokens or at least 20 percent in wall clock** against the off arm's median over the whole set. If the three off-runs disagree with each other about which defects were found, the decision MUST be `re-measure` with the disagreement named, because a gate whose control arm is unstable cannot decide anything. These four answers MUST be fixed before the first A/B run, not argued after a result is in hand. **They are fixed here, with Q9 answered, and the rule is implemented in `reviewer/src/swreview/benchmark/adoption.py`.** Six points the rule needs to be applied mechanically, settled with it and not left to a reader:
  1. **The order the rules fire in is normative**, because more than one can hold at once: the two FR-029 preconditions first (they yield **no decision at all**, a `null` that is an absence and not a fourth value), then control-arm stability, then defects lost, then false alarms, then the repetition count and the presence of a metric, then the threshold. A quality failure therefore decides at any repetition count, while `adopt` is reachable only from a full six-run study.
  2. **"No known defect lost" is measured against what the control arm actually found**, the union of the defect ids matched by any off-run per package, never against the answer key: a defect no off-run ever found was not lost by the lever.
  3. **"No new false alarm" is the on arm's median false-alarm count strictly greater than the off arm's median**, with both arms' worst case printed beside it. Equal medians pass; the asymmetry against the defect rule is deliberate.
  4. **The 20 percent threshold reads the median of the per-run totals over the whole set**, in total tokens (`session.usage.totals.total_tokens` summed over the set's packages, as the scorecard already aggregates it) or in wall clock (`PackageScore.wall_clock_s`, the session's own `started_at` to `ended_at`, summed over the packages, **not** `unattended_runtime_minutes`). Either metric alone suffices; a lever may buy time rather than tokens. The comparison is `(off median - on median) / off median >= 0.20`.
  5. **A study with fewer than three runs in either arm, or with neither a total-token nor a wall-clock median in its scorecards, computes `re-measure`**, never `adopt`: a median and a worst case are not defined over one run, and SC-009 forbids a decision resting on a metric absent from the scorecards.
  6. **A null is never a zero anywhere in the rule.** A median is taken over the non-null values with the contributing row count stated beside it, and a metric with no non-null value is unknown rather than zero.
- **FR-029**: Before any Tier 2 or Tier 3 lever is gated, the benchmark set MUST hold more than the single package it holds today and MUST hold at least one held-out package, and the harness MUST refuse to render a decision for a set that cannot produce a recall number, naming why. The refusal lands in **two** places and both are required: `swreview benchmark run` refuses the run up front, where the lever is chosen and before six paid runs are made, unless the too-small-set override is passed and written into the provenance record; and `swreview benchmark compare` refuses to render the **decision row** for a study whose scorecards produce no recall number or any of whose runs carry that override, while still rendering the raw per-run rows. (VERIFIED: one package, two known defects, not held out, and a package with no geometry, no features, and no equations at all.)
- **FR-030**: Levers 9, 10a **and 11a** MUST be measured by a workstation harness rather than by the benchmark runner, because the benchmark runner iterates pre-built package directories and performs no dump (VERIFIED), which is why `swreview benchmark run` refuses all three by name. Their rows MUST say that the scorecard was not their gate.
- **FR-030a**: The workstation harness MUST write, per arm per repetition, a **run directory of the same shape the benchmark runner writes**, so `swreview benchmark compare` renders these three levers' rows through the same reader as every other lever and no measured lever is absent from the ledger (FR-026, FR-027, SC-010). That directory MUST carry the same provenance record as any other run (FR-030b) and a scorecard-shaped record holding, at minimum: the per-phase dump wall clock from FR-031, the lever's own pass-or-fail precondition verdict (byte-identity for lever 9, `bodies_swept` equality for lever 10a, carried-versus-re-run for lever 11a), and the session usage where a review was run. Token and quality fields the harness cannot produce MUST be null rather than absent or zero, following the same null discipline as every other row. Without this, these three levers produce no run directory, `compare` reads nothing, and they can have no raw rows and no computed decision at all.
- **FR-030b**: The workstation harness MUST take the same `--study`, `--arm` and `--rep` options as `swreview benchmark run` and write them into the provenance record, and MUST be run for the **same number of repetitions per arm as every other lever** (three unless the control arm proved unstable), because FR-028's rule reads medians and worst cases and neither is defined over a single run per arm.
- **FR-031**: Per-phase dump timing MUST exist before levers 9 or 10a are measured, because no dump timing exists anywhere today (VERIFIED: no elapsed measurement in the package writer and counts only in the dump summary), and without it those two levers have no metric at all.
- **FR-032**: The results row of a lever whose off-arm and on-arm are two different commits MUST carry both commits, and the ledger MUST NOT present such a pair as a flag toggle.

Copying removed text into the system prompt file MUST NOT be done. The docstring split MUST be made at an existing paragraph boundary with no rewording, chosen so the first paragraph is already under the enforced cap; a docstring that cannot be split that way MUST be a named exception recorded in the lever's ledger row rather than a silent rewrite.
- **FR-034**: The system prompt MUST render the notes of exactly the tools the adapter is about to be handed, each exactly once, and MUST render none of them when the lever is off.
- **FR-035**: The description cap MUST be enforced by a test that fails the build when a first paragraph is over it, and MUST NOT be enforced by truncating at run time, because a truncation produces a fragment the model reads as a complete sentence.

Byte equality rather than "apart from whitespace" is what makes FR-033's flag-off path reproduce the pre-split wire bytes, and therefore what makes SC-007 hold for lever 2.

**Lever 4, tiered tool exposure (User Story 3)**

- **FR-048**: Tier selection MUST be decidable from the package before the first turn and MUST be fixed for the whole session. A tier that changes the tool list mid-session MUST NOT be built, because it invalidates the prompt prefix from that point and makes two turns structurally different in a way the step log does not record.
- **FR-049**: The "check tools only once evidence exists" tier from the input document MUST NOT be built, because it is a claim about the conversation rather than about the package, and the review plays one opening turn that does the whole review so there is usually no second turn to benefit.
- **FR-050**: The resilient-modeling tier MUST be decided by the same condition the existing resilient-modeling endpoint already refuses on, reused rather than restated, so the two cannot disagree.
- **FR-051**: A withheld tool MUST remain resolvable by the dispatch while being absent from what is sent to the model. A call to it MUST produce the normal started and finished pair, MUST return a result naming the rule that withheld it, and MUST write an **unresolved** coverage entry against the checklist item it would have served, carrying a sentence an engineer can read. It MUST NOT write a failed entry, because failed says the tool broke when we declined to offer it and failed never closes a checklist item.
- **FR-052**: A call to a tool name that never existed MUST still be recorded as a failed tool call, so a hallucinated name and a withheld tool stay distinguishable.
- **FR-053**: The subset MUST be per turn and MUST NOT be per round, so no adapter has to rebuild its tool encoding inside a round and no new source of non-determinism enters the step log.
- **FR-054**: The unresolved count MUST be reported as two numbers, unresolved-because-withheld and unresolved-for-any-other-reason. Adoption requires the second not to rise.
- **FR-055**: The lever's row MUST state the asymmetry of its effect by package class rather than averaging it: 23.8 percent of the payload (8,093 bytes) on a package with no feature rows, and nothing at all on a full assembly package.

**Lever 5, pre-run deterministic checks (User Story 4)**

- **FR-056**: The pre-run MUST cover only the check families that can be enumerated from the package with no model, which on this tree is the three resilient-modeling families and interference (VERIFIED: each already has an entry point that takes no model-chosen selection). A deterministic fastener-joint enumerator MUST NOT be built in this feature; it is a separately specified increment with its own golden fixtures, because a wrong pairing produces a deterministic wrong finding that looks authoritative.
- **FR-057**: Hole alignment MUST NOT be pre-run even where the pairs are enumerable, because that check without a drawing tolerance returns unresolved by design and pre-running every pair would manufacture verdictless unresolved findings. The candidate pairs MUST be named in the digest instead.
- **FR-058**: The pre-run MUST call the same tool functions through the same dispatch the model uses, producing real steps, real findings, real coverage, and real events. A parallel copy of the check logic MUST NOT be written, because it would have to synthesize the provenance every finding cites.
- **FR-059**: The digest MUST be placed in the first user message and MUST NOT be placed in the system prompt.
- **FR-060**: The digest MUST carry counts per check with the non-passing ones named, and a block naming what was **not** evaluated and why. Each not-evaluated line MUST be generated from the same coverage machinery that writes the corresponding skipped coverage item, so the report says the same thing the model was told. It MUST NOT be written as prose maintained separately.
- **FR-061**: A pre-run check that fails MUST NOT stop the review.
- **FR-062**: A package with nothing to pre-run MUST produce a digest that says so, and MUST NOT duplicate the skipped coverage item the existing partial-evidence recorder already writes.
- **FR-063**: The lever's row MUST carry the per-run call counts of the two checks that are never pre-run. A fall in those counts MUST fail the lever regardless of the token saving, because it means the digest suppressed exploration.
- **FR-064**: Levers 5 and 7 MUST NOT be measured in the same arm until each has been gated alone, and lever 6 MUST be measured against a baseline with lever 5 off, because lever 5 removes the round trips lever 6 would have saved.

**Lever 6, parallel tool calls (User Story 4)**

- **FR-065**: The lever MUST mean only that the model may request several tool calls in one round trip. Local execution MUST stay serial and in request order.
- **FR-066**: Tools MUST NOT be executed concurrently. Concurrency would break the step identifier a tool reads when it writes a finding (VERIFIED: it is derived from the current step count, and its own docstring explains that a tool writing a finding is citing the step it is about to be recorded as), would let two findings take the same identifier from a non-atomic allocator, and would make the step log non-deterministic against the golden sessions. Those are silent provenance corruption rather than a crash, and none of them is worth fixing for a thread pool over in-memory list scans.
- **FR-067**: Over-budget calls within a batched round MUST still receive the budget-exhausted output, so the echoed history stays valid and the session remains resumable.
- **FR-068**: The lever MUST be measured on OpenAI only. On Gemini it is a no-op in the on direction and a new capability in the off direction, because the adapter already permits several calls per round and the installed package offers no way to disable it (VERIFIED). The row MUST state that rather than present a fabricated comparison.
- **FR-069**: The lever's row MUST carry both round trips and tool calls, because a model asked to batch may call checks it would otherwise have skipped, which shows as steps rising while round trips fall and can raise false alarms.

**Lever 7, coverage-driven stop (User Story 4)**

- **FR-070**: The stop predicate MUST be defined once and MUST be the same function finalization uses to enumerate open checklist items and open evidence requests, rather than a second copy of that enumeration.
- **FR-071**: For the purpose of stopping early, an item closed only as skipped or out of scope MUST NOT count as closed, although it does for finalization. The two predicates MUST therefore differ deliberately, and the difference MUST carry a comment stating why, so a later tidy-up does not merge them and reintroduce the hole.
- **FR-072**: The stop MUST be implemented by withdrawing the tools for the next round, so every tool call has its output, the history stays valid, and the session can still be continued or have an evidence request answered afterwards. Raising out of a tool call MUST NOT be used: it leaves a call with no output, which the OpenAI history rejects on the next request, and would quietly break the evidence-answering path.
- **FR-073**: The tool result of the round that triggers the stop MUST carry the sentence telling the model that coverage is complete and it should write its closing summary.
- **FR-074**: The scorecard MUST carry the closing coverage bucket mix, shipped with this lever rather than after it, because the failure mode of this lever is a run whose skipped count jumped and which looks efficient in the results table.
- **FR-075**: The lever's row MUST carry how often the stop fired as well as the saving, and adoption MUST require that the skipped and out-of-scope counts do not rise.
- **FR-076**: With levers 6 and 7 both on, the calls already present in the round that closed the last item MUST still run. This is intended and MUST be stated so the measured saving is not read as a defect.

**Lever 8, model tiers per job**

- **FR-077**: Lever 8 MUST NOT be built in this feature. The Ask tab is not ours to route (the embedded terminal runs the engineer's own assistant, which chooses its model), tool-result summarisation does not exist (what exists is a fixed-length truncation with no model in it, VERIFIED), and the one routable job is mechanical and a minority of turns. The record MUST say that this is a scope judgement rather than a measured result. It MUST NOT claim that levers 2 and 4 as specified already shrink the Ask tab's tool payload, because neither reaches it: the Ask tab's tools come from the stdio MCP server, which builds its own narrower list and its own specs directly (VERIFIED: `MCP_TOOL_FUNCTIONS` and `_tool_functions` at `mcp/server.py:103,130-137`, `specs = tuple(spec_for(function) for function in functions)` at `:256`, `_as_tool` reading `spec.description` at `:344-346`), bypassing `ToolRegistry.functions_for`, which is where lever 4 lives; it holds no `EfficiencySettings`; and it has no system prompt to render lever 2's notes into (`instructions` at `:495-499` is a fixed literal). Applying the trim inside `spec_for` to get it anyway MUST NOT be done, both because `_SPECS` is a process-global cache and because it would be an unflagged, unmeasured change to the Ask tab's tool surface, which is what the owner rule forbids. Either the record names this compensation as **not delivered**, or the MCP server MUST take an `EfficiencySettings` of its own defaulting off and apply the same post-`spec_for` trim (FR-039b), measured as its own item with the byte assertion of FR-015 extended to `MCP_TOOL_FUNCTIONS`.

**Lever 9, package reuse (User Story 5)**

- **FR-078**: A reuse key MUST NOT be built from the manifest as it stands. The manifest carries no content hash, no file size, and a hardcoded null modification time with a gap on every document of every dump (VERIFIED), so the input document's key reduces to path and configuration, which says nothing about whether anything changed.
- **FR-079**: If lever 9 proceeds, the manifest MUST gain a file modification time and a file size, each nullable with a gap when the path cannot be read, with the schema version bumped and the schema-model sync test regenerated. If those fields are not added, the lever MUST be dropped rather than keyed on something that cannot detect a change.
- **FR-080**: The key MUST cover the extractor name and version, the schema version, the dump profile, every dump option that changes content, the root document and active configuration, and for every manifest entry in a stable order its document id, configuration, referenced configurations, modification time, and size. It MUST cover every referenced document and not only the root. It MUST be stored on the package so a reader can see what the package claims to be.
- **FR-081**: Each component's suppression state MUST be in the key, because resolving a suppressed or lightweight component changes what a review can see with no file change.
- **FR-082**: Reuse MUST be refused when the active document reports unsaved changes, when any component is not resolved in a way the key cannot express, and when the package carries a phase-level tool error, because a dump that continued past a failed phase writes a package with gaps and nothing in it says the dump aborted.
- **FR-083**: Reuse MUST be refused across a different profile or a different dump option, because a model-check package carries empty holes, fasteners, faces, and bodies by design and reusing it for a full review silently narrows the review.
- **FR-084**: The lookup MUST use an appended index of run folders rather than a scan that parses each package, because a package is tens of megabytes and the existing profile reader deliberately reads only the head of one file on the application thread. A missing or unparseable index MUST mean no reuse, never an error, and the folder and its package MUST be verified to exist before reuse.
- **FR-085**: The key MUST be recomputed at reuse time from the live document's references and MUST NOT be trusted from the file.
- **FR-086**: Reuse MUST be stated in three places: the package (which run it came from and when), the pane status line (naming the run and its age instead of saying it is extracting), and the report header and session record. Reuse MUST never be silent.
- **FR-087**: The gate for this lever MUST be that a reused package is byte-identical to a fresh dump apart from the identifiers, timestamps, and reuse fields that are legitimately new, and that gate MUST be a pass-fail precondition, not a trade against a timing. Which fields are legitimately new MUST be established by dumping an unchanged document twice and diffing (probe P3).

**Lever 10a, lazy meshes (User Story 5)**

- **FR-088**: The tool-envelope check MUST NOT report a clean result when it swept zero bodies; it MUST report unresolved with the reason. This is reachable on today's tree with an existing dump option, it contradicts the module's own statement that a tool envelope that could not sweep a body has not established that the body is out of the way, and it MUST be fixed first, as its own change with its own test, before any lazy-mesh work.
- **FR-089**: Lever 10 MUST be meshes only in this version. Faces MUST NOT be made lazy: with the default face option the extractor describes only faces another dump phase already requested with live handles, so a package with holes and no faces names faces that do not exist; and the geometry fingerprint hashes each component's face parameters, so a package with no faces would move every accepted geometry exception to needs-review on the first lazy run and keep it there, which turns the exception mechanism into noise.
- **FR-090**: A lazy mesh fetch MUST reuse the extractor's existing body-export path rather than a second tessellator, because a different chord tolerance in the two paths would make an envelope answer depend on how the mesh arrived.
- **FR-091**: The bridge command that fetches a mesh MUST have the host choose the file path, MUST be available to the review scope only, MUST keep the existing indistinguishable refusal for an unauthorized scope, and MUST bump the protocol version reported by the handshake. The read-only guard MUST NOT be changed: the tessellation members are not on its denylist and are not covered by its prefixes (VERIFIED), so no guard change is needed and none should be made.
- **FR-092**: Eager extraction MUST remain the default. A lazily extracted package reviewed away from the workstation is a package with less evidence, so the option that reduces evidence is the one that is opted into.
- **FR-093**: A per-review limit MUST bound how many bodies one review may fetch, and reaching the limit MUST be unresolved coverage rather than a stop.
- **FR-094**: A body that cannot be fetched MUST be named in unresolved, never omitted.
- **FR-095**: The gate for this lever MUST be that the tool-envelope check reports the same bodies swept and the same hits in both arms, or reports unresolved naming what it could not fetch. Whether the mesh phase dominates the dump at all is UNVERIFIED and is this lever's entire premise (probe P1), and whether one fetch is usable interactively while it blocks the single worker is UNVERIFIED (probe P2).

**Lever 11a, incremental re-review (User Story 5)**

- **FR-096**: Carry-over MUST reuse the existing fingerprints and MUST NOT introduce a second hashing scheme.
- **FR-097**: Carry-over MUST be limited to the check families whose entire input is inside one existing fingerprint, which on this tree is the resilient-modeling family and nothing else, and MUST exclude the one rule of that family that reads the suppress-test array, which the feature-tree fingerprint does not cover. Every other family reads inputs no fingerprint covers (hole depths and thread designations, a custom property, drawing dimensions and notes, interference settings, and in every case the package gaps, the dump profile, the checklist version, the check version, and the accepted exceptions).
- **FR-098**: The carry-over key MUST be per finding and MUST cover the check, the check's version where it has one, the components, and the fingerprint of those components for the kind that check uses.
- **FR-099**: A carried finding MUST record the session it came from, when it was carried, and the key that justified it, so the decision is reproducible by hand.
- **FR-100**: A carried finding's status MUST NOT be changed. Carry-over is provenance, not status; overloading the status field would break the scorecard's matching rules.
- **FR-101**: Carry-over MUST be recorded in coverage by reusing the checked bucket with a reason that starts by saying it was carried over, rather than by adding a new bucket that would touch the schema, the report renderer, and the scorecard aggregate for the same information.
- **FR-102**: The report MUST name the originating run and MUST state how many findings were carried against how many were re-run, so an engineer can see at a glance which part of the report was not computed today.
- **FR-103**: Carry-over MUST be refused from a session that did not finish; for any finding that is suspected or unresolved; for any finding carrying an engineer's disposition; when any exception touching those components has moved to needs-review; across a change of profile, gap set, checklist version, or check version; and beyond an explicit cap in age or in consecutive runs.
- **FR-104**: The gate for this lever MUST include that every finding touching an edited part was re-run and not carried, and the row MUST carry the carried count per arm, because a lever that improves recall by remembering is not an improvement.

**Lever 12, rules over tokens (User Story 5)**

- **FR-105**: Lever 12 MUST be recorded as standing practice with a review cadence rather than as a task with a flag: a finding class the model keeps producing that a rule can express becomes a deterministic check, and the measurement is the count of findings by check kind over time, which the instrumented scorecard already reports.

**Cross-cutting**

- **FR-106**: No lever MUST be adopted by default in this feature. Shipping a default is a separate decision per lever, taken after that lever's A/B, and recorded in the ledger.
- **FR-107**: The reviewer MUST stay read-only. No lever may add a write to a model, and the extractor's read-only denylist MUST NOT be changed by this feature.
- **FR-108**: Every provider path in this feature MUST go through the existing provider layer with OpenAI as the default and Gemini as the alternative. No part of this feature may use or require Claude.
- **FR-109**: Every live probe MUST be a key-gated test that is skipped without a key and that reports an authentication, rate-limit, or server error as a skip rather than a failure, following the pattern the existing live tests already set.
- **FR-110**: Every claim in the plan and the tasks that derives from an SDK field or an SDK behaviour MUST be marked VERIFIED or UNVERIFIED with the same meanings this spec uses, and an UNVERIFIED claim that gates a decision MUST name the probe that settles it.

### Key Entities

- **Token Usage**: one model round trip's cost as the provider reported it: input, cached input, cache write, output, reasoning or thoughts, tool-result input, total, and latency, every token field an integer or unknown.
- **Usage Round**: one usage record plus the adapter's per-turn round index, the provider, the model, and any cache diagnostic the provider returned.
- **Session Usage**: the round count, the turn count, the totals under the unknown-propagates rule, and the per-turn breakdown.
- **Cache Diagnostic**: the provider's own statement about one request's cache outcome: hit or miss, the miss reason from the provider's enum, and the count of tokens that missed.
- **Efficiency Settings**: the single frozen set of lever flags for one run, every field defaulting to off, recorded on the session.
- **Lever**: a named, independently switchable change with a design, a flag, a test, an A/B metric, a specific counter, and an adoption rule; identified by the number it carries in the input document.
- **A/B Arm**: three runs of one lever in one state (off or on) at one commit, one provider, one model, and one effort, over one benchmark set.
- **Results Ledger**: the rendering of N scorecards into a raw row per run and a decision row per lever, provider, and model, with a decision of adopt, keep off, or re-measure.
- **Package Score Additions**: the usage totals, round trips, cached input share, wall clock, seconds to the first finding, and the closing coverage bucket mix, per package.
- **Withheld Tool**: a tool this run did not offer to the model, its reason sentence, and the checklist item it would have served; resolvable by the dispatch and absent from the wire.
- **Pre-run Digest**: the counts per pre-run check with the non-passing ones named, plus the block naming what was not evaluated and why, generated from the same coverage machinery that writes the matching skipped items.
- **Reuse Key**: the content key that decides whether a previously dumped package may stand in for a fresh dump, with the refusals that the key cannot express stated beside it.
- **Carry-over Key**: the per-finding key that decides whether a previous run's finding may be carried, with the carried provenance recorded on the finding.
- **Probe**: one UNVERIFIED claim and the live test or workstation measurement that settles it, identified by the probe id used in the design brief.

## Assumptions

- The measurement layer lands first and is believed before any caching or behavioural decision is made. It carries no flag, because recording what a run cost is not an experiment.
- The design brief of 2026-09-16 is the authority for every technical claim in this spec, and its VERIFIED labels mean the file and line was read in this tree or in the installed package on that date, never that an API was observed behaving a certain way.
- The installed packages are `openai` 3.13.0 and `google-genai` 2.23.0 under `reviewer/.venv`. A version bump can move a usage field or a cache parameter, and the schema-model sync tests plus the byte-budget test are what would catch it.
- OpenAI is the default provider and Gemini the alternative; both are reached through the existing provider layer. No part of this product uses Claude, and the Ask tab's own model is chosen by the engineer's command-line assistant, not by us.
- The benchmark set as it stands cannot gate anything: one package, two known defects, not held out, and no geometry, features, or equations at all. Growing it is a scheduling decision that precedes every Tier 2 and Tier 3 gate, and it is the precondition most likely to be skipped under time pressure.
- No agent review has ever been run against any package in this tree, so the first measurement of this feature is the baseline itself, and the first run may surface defects in paths that have never executed end to end.
- Three repetitions per arm is the working compromise between provider non-determinism and the cost of a run. If the control arm proves unstable at three, the answer is more repetitions or a better set, not a looser gate.
- Byte counts are not token counts. The estimate of roughly 8,500 tokens per request for the tool array is derived from a byte count and is UNVERIFIED until the first instrumented run replaces it with a real number.
- Levers 9, 10a, and 11a need a workstation with SOLIDWORKS and the pilot design, and they need per-phase dump timing that does not exist today. Without both, those three levers have no metric and are not measurable.
- An adopted lever becomes a default in code with its flag retired or inverted, in a separate change with its own review. This feature ships no lever on by default.
- The engineer running the A/B protocol keeps the tree at one commit for all six runs of a pair, **with no exception**, lever 2 included: its off arm is its flag off, not an earlier commit.
