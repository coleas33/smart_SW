# Feature Specification: Standards Check

**Feature Branch**: `006-standards-check`

**Created**: 2026-09-16

**Status**: Draft

**Input**: User description: "These should be automatically programmatically reviewed as well. Separate pane (Standards Check)" (owner, 2026-09-16), handing over a 2017 VBA release-checklist macro and its description document (both named in `research.md`). Design decided in conversation on 2026-09-16 and recorded in the design brief. The macro's behaviour is reverse-engineered in a check table, described in `research.md` R1, which is normative for what each check means. **That document is not in this repository and is not cited by path**: it reproduces the macro's forty-three constants verbatim, so committing it would put the company's vault layout, library folder names, data-card schema, part-number convention and export-control phrase into a public repository - the disclosure FR-001 exists to prevent. It is held with the owner, beside the macro; `research.md` R1 says what it is and R5 carries the only values from it this repository needs. Appendix A cites it by section name and number, and states enough of each condition to stand alone; every statement in this spec about what the macro does is traceable to a named section of it, listed in Appendix A. `research.md`, and the rest of the feature package, are written in the plan phase; the forward references to it in this spec (the macro's constant values, the workstation probes, the transparency-polarity answer) are obligations on that phase, not facts already recorded. Every probe this spec depends on is also named inline in Assumptions, so the spec stands alone.

A sixth task-pane tab, **Standards**, grades the open document against the company's release checklist: sixteen deterministic checks across parts, assemblies and drawings, instant, with no language model, no API key and no call to any host beyond the local backend. It is a sibling of the Model check tab of feature 003 and reuses its rule-result, coverage, run-folder, exception and pane machinery rather than copying it. Every company-specific value the macro hard-coded (vault root, library folders, data-card property names, the part-number file-name pattern, the revision property name, the revision-table cell location, the export-control phrase, the material configuration name) lives in a **standards profile** outside this repository; the repository ships an example profile with placeholder values and a documented schema.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Parts and Assemblies Graded Against the Release Checklist (Priority: P1)

An engineer has an assembly (or a single part) open. The reviewer grades that document and every part and sub-assembly the evidence package reaches, once per document, against the twelve part, assembly and document checks: the assembly is not left exploded; no assembly document carries rebuild errors; no part carries a rebuild error; no mate has lost a reference; at most one component is fixed; every under-constrained component is either fully mated or, for a library part the profile classifies, carries at least the one or two mates the profile requires; no component is left transparent; no component is left hidden; every sketch is fully defined; every part has a material assigned or a deliberately overridden mass; every cut-list item is excluded from the cut list; and the data-card fields the profile names are filled in on every document whose file name matches the profile's part-number pattern. Each failing check produces exactly one finding for that document, naming every subject that failed it (component instance, mate, sketch feature, feature, cut-list item or field name), the check and what was observed. Checks that pass are checked coverage. Checks with nothing to evaluate are skipped coverage naming the reason. Checks whose evidence the package could not read - a lightweight component, a suppressed component's document, a signal the dump could not obtain - are unresolved coverage naming the reason, never a pass and never silence.

**Why this priority**: It is the bulk of the checklist (twelve of sixteen checks, the data-card check shared with User Story 2 and delivered here), and it is the half of the macro the owner runs most often. It costs ten small additive reads on existing dumpers (enumerated in `contracts/ir-additions.md` section 1, which is where that count is stated) plus one new cut-list dump phase and its IR model. It is a usable product on its own: an engineer can grade a whole assembly before release without the drawing work existing yet.

**Independent Test**: Run the family's single evaluation entry point over two fixture packages and a fictional profile. On the package seeded with one violation of each of the twelve part, assembly and document checks - which therefore seeds both rebuild-error checks, an assembly with a non-zero document-level count and a part with a feature carrying a non-zero error code - confirm eleven findings with the right check ids and subjects, one unresolved row for `standards.assembly.not_transparent` until SC-014 settles the transparency polarity (twelve findings and no unresolved row after it does), and no others. On the compliant package, whose root assembly contains no sub-assembly, confirm zero findings, every one of the twelve checks in checked or skipped coverage with a stated reason, and no unresolved rows other than `standards.assembly.not_transparent` until SC-014 lands. No SOLIDWORKS licence, no drawing evidence and no tab are needed for either.

**Acceptance Scenarios**:

1. **Given** a package whose root assembly records an exploded state, **When** the check runs, **Then** `standards.assembly.not_exploded` fails once naming that document, at error severity.
2. **Given** a package whose root assembly and one sub-assembly each record a non-zero document-level rebuild-error count, **When** the check runs, **Then** `standards.assembly.rebuild_errors` fails once for each of the two documents naming the count as read, and the finding states that the document was not rebuilt before it was read.
3. **Given** a root-assembly mate with three mate entities of which one has no resolved reference, **When** the check runs, **Then** `standards.assembly.mate_references` fails once for that assembly naming that mate and the count of entities that resolved against the count of entities present.
4. **Given** a root assembly with three fixed components, **When** the check runs, **Then** `standards.assembly.one_fixed` fails once for that assembly naming all three components; **Given** exactly one fixed component, **Then** the check is checked coverage.
5. **Given** an under-constrained component that is not produced by a component pattern and whose path matches no library prefix in the profile, **When** the check runs, **Then** `standards.assembly.fully_mated` fails once for that assembly naming that component instance; **Given** the same component under a profile prefix requiring two mates and it carries one unsuppressed mate, **Then** the check fails naming the requirement and the count it found.
6. **Given** a component carrying a component-level transparency override, **When** the check runs and the workstation probe has settled the transparency polarity, **Then** `standards.assembly.not_transparent` fails once for that assembly naming that component instance; **Given** the probe has not settled it, **Then** the check is unresolved naming the unsettled polarity.
7. **Given** a component whose visibility is recorded as hidden and a second component that is suppressed, **When** the check runs, **Then** `standards.assembly.not_hidden` fails naming the hidden component only; the suppressed component is named in the skipped coverage of the checks whose subject it would have been, with its state as the reason, and in the unresolved coverage of every check whose evidence its referenced document would have supplied - never as a hidden finding and never as a pass.
8. **Given** a part with one under-defined sketch that contains no sketch text and a second under-defined sketch that does contain sketch text, **When** the check runs, **Then** `standards.part.sketches_fully_defined` fails once for that part naming the first sketch's feature only, and the second is named in the check's skipped coverage with the sketch-text reason.
9. **Given** a part with two features carrying non-zero error codes and a non-zero document-level rebuild-error count, **When** the check runs, **Then** `standards.part.rebuild_errors` fails once for that document naming both features with their error codes and naming the document-level count as read.
10. **Given** a part with no material assigned and no mass override, **When** the check runs, **Then** `standards.part.material_assigned` fails naming the part; **Given** a part with a material assigned and a mass override, **Then** the check fails naming both; **Given** no material and a mass override, or a material and no override, **Then** the check is checked coverage.
11. **Given** a part with two cut-list items of which one is not excluded from the cut list, **When** the check runs, **Then** `standards.part.cut_list_excluded` fails once for that part naming that item only; **Given** a part with no cut-list items, **Then** the check is skipped coverage with the reason.
12. **Given** a part whose file name matches the profile's part-number pattern and whose data card leaves one profile field blank and omits another, **When** the check runs, **Then** `standards.document.data_card_complete` fails once for that document naming the blank field as blank and the omitted field as missing; **Given** a file name that does not match the pattern, **Then** the check is skipped coverage naming the file-name convention.
13. **Given** a part reached only through lightweight or suppressed component instances, **When** the check runs, **Then** every part-scope check for that document is unresolved coverage naming the component state, and no check reports it as passing; **Given** the same part reached through one resolved instance and one lightweight instance, **Then** it is graded normally and the lightweight instance is named in the finding's coverage limits.
14. **Given** a part reached through twenty component instances, **When** the check runs, **Then** each failing check produces exactly one finding for that document naming all twenty instances, and contributes one to the error count.
15. **Given** a sub-assembly, **When** the check runs, **Then** `standards.assembly.mate_references` is unresolved for that sub-assembly naming it and the missing sub-assembly mate data, and the mate-count branch of `standards.assembly.fully_mated` is unresolved for its under-constrained components whose paths match a one-mate or two-mate prefix, naming the same gap; every other component of that sub-assembly is decided on its constrained status exactly as in the root assembly, and `standards.assembly.one_fixed`, `standards.assembly.not_transparent`, `standards.assembly.not_hidden`, `standards.assembly.not_exploded`, `standards.assembly.rebuild_errors` and `standards.document.data_card_complete` are evaluated for it.
16. **Given** a part whose path matches a library-skip prefix in the profile, **When** the check runs, **Then** the four part checks and the data-card check appear for it as skipped coverage naming the prefix that matched, never as passes; **Given** an assembly document under the same prefix, **Then** it is graded normally, as the macro graded it.
17. **Given** a part with an under-defined sketch inside a derived feature and a sub-feature carrying a non-zero error code, **When** the check runs, **Then** both are found and each finding names the chain of parent features that reaches the subject, so the engineer can open it.

### User Story 2 - Drawings Graded Against the Release Checklist (Priority: P2)

An engineer has a drawing open. (A package a colleague produced, or one the command line is handed, can carry a drawing record too; it is graded the same way.) The reviewer grades every drawing against the four drawing checks and the data-card check: no display dimension carries a manual override; no annotation is dangling; the revision on the drawing's revision table, the revision property on the drawing and the revision property on every model the drawing references all agree; no export-control statement appears in the drawing's notes; and the data card is complete. The drawing checks need evidence that does not exist today, so this story also delivers a native drawing dump phase: sheets, views and the documents they reference, display dimensions with their override flags, units and values, annotations with their identities and dangling flags, revision-table rows and note text - and, for a drawing-rooted dump, the model phases over each referenced model so the part and assembly checks can grade it. The macro force-rebuilt every drawing before reading it; this feature never rebuilds anything and the report says that the drawing was read as it stood.

**Why this priority**: It is the other half of the checklist and the half the owner runs at release time, but it is the more expensive half: a second new extraction phase over a document kind the extractor has never read, eight new IR models (`DrawingRecord`, `DrawingSheetRecord`, `DrawingView`, `DisplayDimensionRecord`, `DrawingAnnotation`, `DrawingNote`, `RevisionTable`, `RevisionTableRow` - listed in `data-model.md` section 2.3, and with `CutListItem` the nine new `$defs`) and four workstation probes. Parts and assemblies deliver value without it.

**Independent Test**: Run the evaluation entry point over a fixture package that contains a hand-written three-sheet drawing record with one overridden dimension, one dangling annotation, a revision table whose last row disagrees with the drawing's revision property, and an export-control phrase in a note on sheet 3. Confirm four findings with the right check ids, severities and subjects, and confirm a second, compliant drawing fixture yields five checked-coverage rows. No SOLIDWORKS licence is needed; the drawing dumper itself is verified separately by its own unit tests against a fake drawing source and by the workstation probes.

**Acceptance Scenarios**:

1. **Given** a drawing with one display dimension whose override flag is set, **When** the check runs, **Then** `standards.drawing.dimensions_not_overridden` fails once for that drawing naming the sheet, the view, the dimension and its override value rendered with the unit the package recorded it in.
2. **Given** a drawing with two dangling annotations on different sheets, **When** the check runs, **Then** `standards.drawing.annotations_not_dangling` fails once for that drawing naming each annotation with its sheet, view, annotation type and identity.
3. **Given** a drawing whose revision table's last data row disagrees with the drawing's revision property and whose revision property also disagrees with the referenced model's revision property, **When** the check runs, **Then** `standards.drawing.revision_matches` produces one warning-severity finding for that drawing naming both disagreements, each with both values and their source.
4. **Given** a drawing with no revision table on any sheet, **When** the check runs, **Then** `standards.drawing.revision_matches` produces a warning-severity finding stating that no revision table was found.
5. **Given** a drawing whose revision table contains only its header row, **When** the check runs, **Then** the revision read from that table is the profile's initial-revision value and is compared against the drawing's revision property as normal, rather than reported as a mismatch.
6. **Given** a drawing whose notes contain the profile's export-control phrase on any sheet, in any view or sheet format, **When** the check runs, **Then** `standards.drawing.no_itar_statement` produces one warning-severity finding for that drawing naming the sheet and the note.
7. **Given** a drawing with no views at all, or whose views reference no document, **When** the check runs, **Then** `standards.drawing.revision_matches` is unresolved for the model comparison naming the missing referenced document, the drawing's own checks still run, and nothing crashes.
8. **Given** a drawing whose sheets, dimensions, annotations, revision table or notes the dump could not read, **When** the check runs, **Then** each affected check is unresolved coverage naming exactly what could not be read.
9. **Given** a drawing in the package whose views reference an assembly, **When** the check runs, **Then** that assembly is graded by the assembly checks of User Story 1 exactly once, every part and sub-assembly reachable through its component tree is graded once, and a document reached both this way and from the root is not graded twice.
10. **Given** a drawing whose views reference two different models, **When** the check runs, **Then** both are graded and both revisions are compared, and a disagreement on either is named in the one revision finding for that drawing.
11. **Given** a drawing whose referenced model is not loaded in the session, so the dump could not extract it, **When** the check runs, **Then** the dump records a gap naming that model, the part and assembly checks for it are unresolved coverage naming the same gap, and nothing is opened or resolved to fill it.
12. **Given** a drawing whose only sheet evidence came from the PDF ingest rather than the native drawing phase, **When** the check runs, **Then** the four drawing checks are unresolved coverage naming the evidence source, because a parser with known limits may not be graded as a demonstrated finding.
13. **Given** any drawing run, **When** the report is written, **Then** it states that the drawing was read as it stood and was not rebuilt.

### User Story 3 - The Standards Tab (Priority: P3)

An engineer presses **Standards** in the task pane with a document open and, in seconds, gets a release verdict for that document: a headline that reads "ready to release" only when there are no errors, the counts in every coverage bucket beside it, then the list of all sixteen checks with each one's coverage (checked, failed, warned, skipped, unresolved, out of scope) and reason, then the findings, each with its subjects and a **Show in SOLIDWORKS** button. Nothing on this path constructs a language-model provider, reads an API key or calls any host beyond the local backend. The run writes a run folder, so the same result can be read back after SOLIDWORKS or the pane has been restarted. The tab is the sixth tab; none of the five existing tabs is removed, hidden or reordered.

**Why this priority**: It is the surface the owner asked for, but it is worthless without the checks behind it, and both earlier stories are fully testable through the evaluation entry point without it.

**Independent Test**, in two halves. **Offline**, against the fake session and host seams the existing host tests already use: the page-to-host envelope and every refusal, the verdict and counts the header renders, the sixteen-row check list, the escaping of untrusted strings, the read-back of a completed check by its id from a run folder on disk, the tab inventory and order, and the banner and tooltip. **[W] On the workstation**: press Standards on a real document, confirm the run folder is created and registered as the pane's latest run, press Show on one finding's subject and confirm the entity is selected or `ok: false` is reported naming what could not be reached, then restart the pane and read the same check back by its id.

**Acceptance Scenarios**:

1. **[W] Given** an assembly open and the add-in attached, **When** the engineer presses Standards, **Then** the host dumps the open document with the `Standards` dump profile, writes and registers a check run folder, and replies with the document, the configuration and the counts it extracted; the page then asks the backend for the result itself.
2. **Given** a completed run with zero error-severity findings and zero unresolved rows, **When** the page renders, **Then** the headline reads "ready to release" with the error count 0 and the counts in every other bucket shown beside it.
3. **Given** a completed run with one or more error-severity findings, **When** the page renders, **Then** the headline reads "not ready to release", never "ready", regardless of how many checks passed, and the unresolved check ids are shown beside the counts in this state as in every other.
4. **Given** a completed run with zero errors but one or more unresolved checks, **When** the page renders, **Then** the headline says the release verdict is incomplete and names every unresolved check id beside it; no headline claims readiness while coverage is unknown.
5. **Given** a completed run in which errors were waived by accepted exceptions, or checks were skipped because a profile list is empty, or the package carried no drawing, **When** the page renders, **Then** the headline names the waived count, the skipped count and "no drawing graded" as applicable, so a clean headline never hides them.
6. **Given** any completed run, **When** the page renders, **Then** all sixteen checks appear in the check list, each showing every bucket it landed in with the documents in that bucket and the per-document reason, and no letter grade and no single percentage is rendered as the result.
7. **[W] Given** a finding with a subject that resolves to a SOLIDWORKS entity, **When** the engineer presses Show on it, **Then** the shared resolver selects that entity, or replies `ok: false` naming the entity it could not reach; nothing reports success while selecting nothing.
8. **Given** a subject with no selectable entity - a data-card property name, a note, a revision-table row, a cut-list item, a mate, or any drawing entity in a drawing that is not the active document - **When** the page renders it, **Then** no Show control is rendered for that subject at all, rather than one that reports `ok: false` every time.
9. **Given** a subject reached through more than one component instance, **When** the page renders it, **Then** the control says which instance it will act on and cycles to the next.
10. **Given** the engineer presses the report, folder or log control, **When** the host handles it, **Then** the action is delegated to the shared pane actions with the path taken from the host's own record, never from the page.
11. **Given** no document is open, a document the add-in is not attached to, a document that has never been saved, or a document kind that is not a part, an assembly or a drawing, **When** the engineer presses Standards, **Then** the tab refuses naming the reason with its error class and writes no run folder.
12. **Given** no standards profile is configured, or the configured file cannot be read, **When** the engineer presses Standards, **Then** the host refuses before it dumps anything, naming the profile path, and writes no run folder; **Given** a configured, readable profile that fails its schema, **Then** the backend refuses naming the path and the schema error, the run folder created before the dump is reported as an empty run rather than as a result, and the checks never fall back to built-in company values because there are none.
13. **Given** the backend is not running, **When** the engineer presses Standards, **Then** the tab reports it and offers the log, exactly as every other pane surface does; there is no second transport.
14. **Given** the engineer switches the active document, **When** the host sends `document.changed`, **Then** the tab updates what it says it can grade, so it never offers a button the host will refuse.
15. **Given** the language-model provider factories are monkeypatched to raise, **When** a standards check runs, **Then** it completes unchanged.
16. **Given** a component named with markup such as `<img src=x onerror=alert(1)>` or an observed string containing `</script>`, **When** the page renders it, **Then** it appears as text and executes nothing, through the same shared DOM helpers the other pages use.
17. **Given** a completed run and a restarted pane, **When** the check is read back by its id, **Then** the same verdict, checks, coverage and findings are returned from the run folder.
18. **Given** the pane loads, **When** the tabs are inspected, **Then** the Review, Ask, Extract, Model check and Remodel tabs are all still present, unchanged and in that order with Standards sixth; the Standards tab carries one purpose sentence as both its banner and its tooltip, stating that it needs no AI and no key; its content is created on first activation from a named placeholder note rather than at add-in load; and the tool list the MCP server exposes, the terminal profile's enabled tools and the function list are unchanged, with the existing tests that pin them passing unedited.

### User Story 4 - Waivers and the Command Line (Priority: P4)

An engineer accepts a deliberate deviation once, with a note, and it stays accepted on the next run. A team lead runs the same checks headlessly over a package on a machine without a SOLIDWORKS licence, in continuous integration or over a package a colleague produced, and gets the same findings and the same verdict. A flat waiver file naming check ids and reasons can be imported against a run, accepting every matching failing finding at once and reporting every id that matched nothing.

**Why this priority**: The tab is usable without it - an engineer can read the findings and judge them - but real models carry deliberate deviations and the checklist is only trusted once they can be recorded. Headless running also makes the checks runnable on the pilot's cheap machines.

**Independent Test**: Over a fixture package, run `swreview check standards --package <dir> --out <dir> --profile <fictional.yaml>`, confirm the package directory's bytes are unchanged, the run folder holds the session, report and check record, and the exit code is 0; accept one failing check with a note through the command that writes `exceptions.json` beside the package; run again into a new folder and confirm the acceptance was applied and the check is reported as checked within scope carrying the exception id; import a waiver file naming a failing check id, a check id that did not fail, a warning-severity check id and an unknown id, and confirm the four outcomes, that nothing is written, and that the command exits 1.

**Acceptance Scenarios**:

1. **Given** a package and an output directory, **When** `swreview check standards` runs, **Then** it writes the session, the report and the check record into the output directory, writes nothing into the package directory, prints findings and coverage in the same human and JSON shapes the other check commands print, and exits 0 with violations in the output rather than in the exit code.
2. **Given** a package that does not record the phases the standards checks read, **When** the command runs, **Then** it refuses with exit 1, naming the profile that produced the package and the phases that are missing, rather than reporting sixteen unresolved checks that read as a broken model.
3. **Given** no `--profile` argument, **When** the command runs, **Then** it uses the configured profile path and, if none is configured or the file is absent, unreadable or schema-invalid, refuses with exit 1 naming the path and the reason.
4. **Given** an error-severity finding, **When** the engineer accepts it with a note, **Then** an exception is recorded bound to the finding's document, its component instances, its configuration and a fingerprint of the check's inputs, the control states that the acceptance waives the check for that document and not for one subject, and the next run reports the check as checked within scope carrying the exception id and reason.
5. **Given** a check accepted on a document and a second, newly seeded subject of the same check on the same document, **When** the next run happens, **Then** the fingerprint no longer matches, the finding stands and names the exception as needing re-review, and it is never silently silenced.
6. **Given** a warning-severity finding (`standards.drawing.revision_matches` or `standards.drawing.no_itar_statement`), **When** the page renders it, **Then** no Accept control is rendered at all, and an accept request for it is refused naming the severity.
7. **Given** an empty note, **When** an accept is attempted, **Then** it is refused.
8. **Given** an acceptance recorded on one drawing, **When** the same check fails on a different drawing, **Then** it still fails, because the exception is bound to the drawing document it was accepted on.
9. **Given** a waiver file naming a failing check id, a check id that did not fail, a warning-severity check id and an unknown id, **When** it is imported, **Then** the four are reported as `would accept`, `unused`, `invalid (warning check)` and `invalid (unknown check)`, nothing is written, and the command exits 1 because two ids were invalid; **Given** a waiver file whose every id is valid, **Then** the matching ids are reported as `accepted <n>`, the file is written and the command exits 0.
10. **Given** a previous standards run under the same run root whose package carries the same design id, **When** a new run folder is created, **Then** that run's exception store is copied into the new folder before the checks run; a missing candidate is reported and is not an error, and an unreadable candidate refuses the run.
11. **Given** a standards check record and a model check record under the same run root, **When** either is read back by its id, **Then** the record's family field decides which result shape is returned and neither family answers for the other.

### Edge Cases

**Traversal and document state**

- The open document is a part, so no assembly check applies: the seven assembly checks are out-of-scope coverage naming the document kind, not passes.
- The open document is a part or an assembly and the package carries no drawing: the four drawing checks are out-of-scope coverage naming that the run graded no drawing, and the headline says "no drawing graded" beside the verdict, so a release verdict never implies a drawing was checked when none was.
- The open document is a drawing: the drawing checks run on it, and every document its views reference is graded as a part or an assembly exactly once - including, for a referenced assembly, every part and sub-assembly reachable through its component tree; the same document reached again from the root is not graded twice.
- The open document is open but has never been saved: the run is refused naming the document, because there is no path to match against the profile's library prefixes or part-number pattern. The macro silently did nothing here because it decided document kind from the last three characters of the path.
- A document *reached by the traversal* with no recorded kind, or no path - a virtual component, a library-feature part, a kind that is not a part, an assembly or a drawing: unresolved coverage for every check that would have applied to it, named once per document. It never refuses the whole run; only the root document can do that.
- The same part reached through twenty instances, or through two different sub-assemblies: graded once; every finding names every instance that reaches it.
- A component instance suppressed in the reviewed configuration: named in the skipped coverage of the checks whose subject it would have been, with "suppressed in <configuration>" as the reason, and in the unresolved coverage of every check whose evidence its referenced document would have supplied; it is never a hidden finding and never a pass.
- A lightweight or unloaded component: the same, with the component state as the reason; the reviewer never resolves it.
- A document reached through at least one resolved instance and one unresolved instance: graded normally, with the unresolved instances named in the finding's coverage limits rather than making the document unresolved.
- A component whose referenced document is missing from the package entirely: an unresolved row naming the component and the missing document, once per document.
- A sub-assembly appearing under two parents: one set of assembly rows for that document, naming both paths.
- A document whose path matches prefixes in more than one of the profile's lists: each list is matched independently, because they answer different questions - the skip list and the sketch-exempt list are not in competition with the mate-count lists. Within one list the longest matching prefix wins and every match in that list is named in the coverage reason; the profile schema states this rule, because the macro's one-mate list was tested before its two-mate list and relied on that ordering to give a specific fastener folder a different requirement from its parent folder.
- A profile prefix that does not end in a path separator: it is still a prefix match, so it matches that file and any path that starts with it, exactly as the macro's did; the profile schema says so, because the macro's lists mixed folder prefixes with one single file path.
- Path comparison is case-insensitive and normalized, so a prefix written in a different case still matches.

**Per-check boundaries**

- An assembly with no mate group at all: `standards.assembly.mate_references` is skipped coverage with the reason "no mates", and `standards.assembly.fully_mated` still runs on constrained status.
- A mate whose entity count the package could not read: unresolved for that mate, naming it.
- A mate suppressed in the reviewed configuration: not counted toward the one-mate and two-mate minimums, and named in the coverage reason for the components it touches.
- A component whose constrained status the package records as unknown or unavailable: `standards.assembly.fully_mated` is unresolved for it.
- A component produced by a component pattern: skipped coverage for `standards.assembly.fully_mated`, naming the pattern. A component whose pattern origin cannot be determined: unresolved, not a finding.
- A root component, or the synthesized root of a part opened alone, which has no constrained status by design: not a subject of `standards.assembly.fully_mated`.
- A part with no sketches at all: `standards.part.sketches_fully_defined` is skipped coverage with the reason.
- A sketch whose constrained status is unknown (for example with automatic solving off): unresolved for that sketch.
- A sketch inside a hole-wizard feature: evaluated, and the finding names the hole-wizard feature as well as the sketch, so the engineer can find it.
- A sketch or a feature nested inside a derived, library or pattern feature: evaluated like any other, and the finding names the chain of parent features that reaches it so the engineer can open it.
- A sketch whose text-segment presence could not be read: unresolved for that sketch, because the sketch-text exemption can then neither be applied nor ruled out.
- A part whose material the package recorded in a configuration other than the profile's material configuration: `standards.part.material_assigned` is unresolved naming both configurations, because the standard is about the configuration the profile names; a part that has no such configuration is unresolved naming the missing configuration.
- A part whose mass-override state could not be read: `standards.part.material_assigned` is unresolved, because pass and fail differ only by that flag.
- A cut-list folder that holds no bodies, and which SOLIDWORKS therefore does not display: not a subject.
- A cut-list item whose exclusion flag could not be read: unresolved for that item.
- A document-level rebuild-error count that could not be read: the rebuild-error check for that document is unresolved for the document-level half; the per-feature error codes do not substitute for it, because the document count also covers mate errors that no feature carries.
- A drawing sheet with no views: its dimension and annotation checks contribute nothing and the sheet is named in the coverage reason; it is not a crash and not a pass.
- A drawing whose first real view is on a later sheet: every sheet is read, so the referenced document is still found.
- A drawing referencing more than one document: every referenced document is graded and its revision compared; disagreements on any of them are named in the one revision warning for that drawing.
- A revision-table cell that is empty: compared as empty and reported as a mismatch naming the empty cell, never normalized into a pass.
- A revision table whose last data row is still its header row: the revision read from that table is the profile's initial-revision value, and is compared against the drawing's revision property as normal.
- A drawing with more than one revision table: every table is read and each is compared, naming its sheet.
- A note whose text could not be extracted: `standards.drawing.no_itar_statement` is unresolved naming the note, because an unread note cannot be shown not to carry the statement.
- A data-card field whose value resolves to whitespace only: reported as blank.
- A data-card field that carries a value only in a configuration-specific property: the check reads the configuration-independent properties, as the macro did, and names that scope in the observed text.
- A document whose file name matches the part-number pattern but whose custom properties the package could not read: unresolved, not a pass.
- A profile whose part-number pattern is absent or empty: `standards.document.data_card_complete` is skipped coverage naming the empty setting, as the other empty-list settings are.

**Profile, run and tab**

- A profile with an empty **selecting** setting - an empty data-card field list, an empty part-number pattern, an empty revision property or an empty export-control phrase: valid; there is nothing left to test, so the checks that depend on it report skipped coverage naming the empty setting, the skipped count travels on the headline, and an unconfigured profile never silently **passes** a document.
- A profile with an empty **library** list - `skip_prefixes`, `sketch_exempt_prefixes`, `one_mate_prefixes` or `two_mate_prefixes`: valid; an exemption list that is empty exempts nothing and a mate-count list that is empty reclassifies nothing, so every check that would have been affected **runs on every document it applies to**. An empty exemption list is never itself a skip, because that would let an unconfigured profile silently **grade nothing** - the same failure in the other direction.
- A profile whose library prefixes are written relative to the vault root: resolved against the vault root before matching, so one profile is portable between machines; a prefix that is already absolute is matched as written.
- A profile naming a vault root that does not exist on this machine: accepted, because a package can come from another machine; the prefix match is textual.
- Two runs in the same second on the same document: the second run's folder id is disambiguated by the run-folder helper with a numeric suffix rather than reusing or refusing the colliding id, so two records never share an id and the page always reads back the run it asked for.
- A run root holding both standards and model check folders: reading one by id never returns the other family's shape, and each tab's latest-check field names only its own family's newest folder.
- Folder proliferation: one folder per check, as with the Model check tab; no automatic sweep is built in this version.
- A check accepted on one document and then that document appearing under a different parent: the exception is bound to the document and its instances, so it applies wherever the document is reached.

## Requirements *(mandatory)*

### Functional Requirements

**The standards profile**

- **FR-001**: Every company-specific value the checks need MUST come from a **standards profile** file that is not committed to this repository: the vault root, the library-folder prefixes whose part documents are skipped, the library prefix list that requires at least one mate and the list that requires at least two, the library prefix list exempt from the sketch check, the data-card property names, the part-number file-name pattern (using `#` for one digit and `?` for one character, the vocabulary the macro's pattern used), the revision property name, the initial-revision value, the revision-table header text, the revision-table cell location (a row selector counted from the end and a column index, so a different drawing template does not silently read the wrong cell), the material configuration name, and the export-control phrase. Library prefixes MAY be written relative to the vault root and MUST then be resolved against it before matching; an absolute prefix is matched as written. The repository MUST ship an example profile with fictional placeholder values and a documented schema, tests MUST use a fictional profile fixture, and no value from the owner's real profile may appear in any source file, test, fixture, golden, contract or example profile in this repository; the values the macro carried are recorded once, in `research.md`, as "the values to be entered into the profile". The profile path MUST be a setting with a documented default under the user's local application data. There MUST be no built-in fallback values, because a fallback would silently grade a document against the wrong standard.
- **FR-002**: The profile MUST be validated in exactly one place - the reasoning side, which owns the schema - so the schema is never expressed twice. The host MUST check only that a profile path is configured and the file is readable, and MUST refuse before it creates a run folder or dumps anything when it is not, naming the path with its error class. The backend MUST validate the schema and return the named schema error, which the page renders; a run folder created before that refusal MUST be reported as an empty run rather than as a result. A missing, unreadable or schema-invalid profile MUST refuse the run either way, and MUST never be substituted for.

**Traversal, scope and finding granularity**

- **FR-003**: The checks MUST evaluate every document the evidence package reaches **exactly once**, not once per component instance: the root document, every part and sub-assembly document reachable through the component tree, and, for a drawing, every document any view on any sheet references and - where a referenced document is an assembly - every part and sub-assembly reachable through its component tree. A document reached both from the root and from a drawing's referenced model MUST still be graded once. **A failing check MUST produce exactly one finding per document**, carrying every subject that failed it and naming every component instance through which that document is reached; a finding MUST contribute one to its severity count regardless of how many subjects it carries or how many instances reach it. This is the only counting rule; no check states a different one.
- **FR-004**: The document kind MUST come from the package's recorded document kind, and the check sequence MUST follow it: assembly documents receive the seven assembly checks and the data-card check; part documents receive the four part checks and the data-card check; drawing documents receive the four drawing checks and the data-card check. A **root** document whose kind the package does not record, or which has no path, MUST refuse the run naming the document and the reason. Any **other** document the traversal reaches whose kind or path the package does not record MUST be unresolved coverage for every check that would have applied to it, naming the document and the component instances that reach it, never silently skipped and never a refusal of the whole run.
- **FR-005**: A component instance that is suppressed, lightweight, unloaded or otherwise unresolved MUST be handled by exactly one rule, stated here and cited rather than restated by the individual checks. For a check whose evidence comes from the instance's **referenced document** - `standards.assembly.not_exploded`, `standards.assembly.rebuild_errors`, the four part checks and the data-card check for that document - the instance MUST produce an **unresolved** coverage row naming the component, its state and the evidence that was therefore missing. For a check whose subject is the **instance itself** and whose signal the package records on the instance - `standards.assembly.one_fixed`, `standards.assembly.fully_mated`, `standards.assembly.not_transparent`, `standards.assembly.not_hidden` - the instance MUST NOT be a subject and MUST be named in that check's **skipped** coverage with its state as the reason, because a component suppressed out of the reviewed configuration is not part of the assembly being graded; where the signal itself could not be read the row is unresolved instead. A suppressed instance MUST NOT produce a pass, a silent skip, or a finding of any other check, and the reviewer MUST NOT resolve, load or open it to obtain the evidence. A document reached through at least one resolved instance MUST be graded normally, with the unresolved instances named in the finding's coverage limits.
- **FR-006**: Profile prefix matching MUST be case-insensitive, path-normalized, anchored at the start of the path, and resolved **independently within each of the profile's four lists**; a match in one list never cancels a match in another. Within one list the longest matching prefix decides and every match in that list is named in the reason. A prefix is a prefix, whether or not it ends in a path separator. A match on the **skip** list MUST make the four part checks and the data-card check **skipped** coverage naming the matched prefix, and MUST apply to **part documents only** - an assembly document under a skip prefix is graded normally, as the macro graded it. A match on the **sketch-exempt** list MUST make `standards.part.sketches_fully_defined` skipped coverage naming the prefix and MUST affect no other check. A match on a **mate-count** list MUST change only `standards.assembly.fully_mated`'s requirement for that component and MUST skip nothing; where a path matches prefixes in **both** mate-count lists, the **longest** matching prefix across the two decides, and on an exact length tie the one-mate requirement wins - one rule rather than a second, and never evaluation order. An **empty** list MUST NOT itself skip anything: an empty skip, sketch-exempt or mate-count list exempts and reclassifies nothing, so every check it would have affected runs on every document it applies to.

**The sixteen checks**

Each check below states its fail condition, its checked condition, its skipped conditions and its unresolved conditions. Every one produces at most one finding per document, per FR-003.

- **FR-007**: `standards.assembly.not_exploded` MUST fail, at **error** severity, once per assembly document the traversal reaches whose recorded exploded state is exploded, naming that document. It MUST be **checked** coverage for an assembly document whose recorded exploded state is not exploded, and **unresolved** naming the reason when the field is absent and the dump recorded a gap for it. It MUST be **out-of-scope** coverage naming the document kind for part and drawing documents.
- **FR-008**: `standards.assembly.rebuild_errors` MUST fail, at **error** severity, once per assembly document whose recorded document-level rebuild-error count is greater than zero, naming the document and the count, and the finding and the report MUST state that the count is what the document carried as it stood and that nothing was rebuilt. It MUST be checked coverage at a count of zero and **unresolved** naming the reason when the count could not be read; per-feature error codes MUST NOT be substituted for it, because the document count also covers mate errors that no feature carries. It MUST be out-of-scope coverage naming the document kind for part and drawing documents.
- **FR-009**: `standards.assembly.mate_references` MUST fail, at **error** severity, once per assembly document that has one or more mates whose count of mate entities with a resolved reference is less than its count of mate entities, naming every such mate, both counts and the entities that did not resolve. It MUST be skipped coverage naming "no mates" for an assembly with no mates recorded, **unresolved** for any mate whose entity or reference data could not be read, and **unresolved** for every sub-assembly whose mates the package does not record, naming that sub-assembly.
- **FR-010**: `standards.assembly.one_fixed` MUST fail, at **error** severity, once per assembly document whose immediate child components include **more than one** fixed component, naming every fixed component. It MUST be checked coverage at zero or one fixed component, skipped coverage for an assembly with no child components, and **unresolved** naming the components whose fixed state could not be read. Suppressed and unresolved instances are handled by FR-005.
- **FR-011**: `standards.assembly.fully_mated` MUST evaluate every immediate child component of every assembly document whose constrained status is under-constrained, skipping components produced by a component pattern (naming the pattern in the skipped coverage). For a component whose path matches no mate-count prefix in the profile the check MUST fail, at **error** severity, once per assembly document naming every such component. For a component whose path matches a one-mate or two-mate prefix the check MUST fail when its count of **unsuppressed** mates is below that minimum, naming the component, the requirement and the count found. It MUST be checked coverage for a component that is fully or over constrained, and **unresolved** for a component whose constrained status, pattern origin or mate count could not be read; and, because the package records only the root assembly's mates, **unresolved** for an **under-constrained** component of a sub-assembly whose path matches a one-mate or two-mate prefix, naming that sub-assembly and the missing sub-assembly mate data. Every other component of a sub-assembly MUST be decided on its constrained status exactly as in the root assembly: under-constrained with no matching mate-count prefix fails, fully or over constrained is checked coverage, and a pattern instance is skipped coverage. Suppressed and unresolved instances are handled by FR-005.
- **FR-012**: `standards.assembly.not_transparent` MUST fail, at **error** severity, once per assembly document naming every immediate child component that carries a component-level transparency override indicating transparency. **Once the polarity is settled**, a component with no component-level appearance override MUST be checked coverage; while it is unsettled no component can be, because the polarity decides how the recorded value is read for every component, including one with no override. The check MUST be **unresolved**, naming the reason, for any component whose override could not be read, and for every component until the workstation probe named in Assumptions has settled which value of the recorded override means transparent; the polarity MUST NOT be assumed from the macro's condition. Suppressed and unresolved instances are handled by FR-005, which differs from the macro here (difference c).
- **FR-013**: `standards.assembly.not_hidden` MUST fail, at **error** severity, once per assembly document naming every immediate child component whose recorded visibility is hidden. Suppression MUST NOT be treated as hidden: a suppressed component is FR-005's row, not a finding of this check. The check MUST be **unresolved** naming any component whose visibility could not be read.
- **FR-014**: `standards.part.sketches_fully_defined` MUST fail, at **error** severity, once per part document that has one or more sketches whose recorded constrained status is under-defined, naming every such sketch feature, the chain of parent features that reaches it, and, where the sketch belongs to a hole-wizard feature, that feature too. **Every sketch the package records is a subject, at any depth in the feature tree** (difference z). A sketch that contains at least one text segment MUST be **skipped** coverage naming the sketch-text exemption. A part whose path matches the profile's sketch-exempt library prefixes MUST be skipped coverage naming the prefix, and a part with no sketches skipped coverage with that reason. A sketch whose constrained status or text-segment presence could not be read MUST be **unresolved**.
- **FR-015**: `standards.part.rebuild_errors` MUST fail, at **error** severity, once per part document that has one or more features carrying a non-zero error code, or whose recorded document-level rebuild-error count is greater than zero, naming every such feature with its code and the chain of parent features that reaches it, and naming the document-level count as read. **Every feature the package records is a subject, at any depth in the feature tree** (difference z). It MUST be checked coverage when every feature's code is zero and the document count is zero, and **unresolved** naming the features whose error code could not be read or the document count that could not be read. The finding and the report MUST state that the counts are as the document stood and that nothing was rebuilt.
- **FR-016**: `standards.part.material_assigned` MUST fail, at **error** severity, once per part document that has **neither** a material assigned **nor** an overridden mass, and for a part that has **both**, naming which of the two conditions held. A part with exactly one of them MUST be checked coverage. The material compared MUST be the one the package recorded for the profile's material configuration; when the configuration the package recorded the material in is not the profile's material configuration, or the document has no such configuration, the check MUST be **unresolved** naming both configurations. The check MUST also be **unresolved** naming the reason when the material name or the mass-override state could not be read, because pass and fail differ only by those two signals.
- **FR-017**: `standards.part.cut_list_excluded` MUST fail, at **error** severity, once per part document that has one or more cut-list items not marked excluded from the cut list, naming every such item and its folder. Cut-list items MUST be identified from the package's cut-list records structurally, not by matching a feature name (difference bb). Cut-list folders that hold no bodies, and are therefore not displayed, MUST NOT be subjects. A part with no cut-list items MUST be skipped coverage with that reason, and an item whose exclusion flag could not be read MUST be **unresolved**.
- **FR-018**: `standards.drawing.dimensions_not_overridden` MUST fail, at **error** severity, once per drawing document that has one or more display dimensions whose override flag is set, naming every such dimension with its sheet, its view, its identity and its override value rendered with the unit the package recorded it in. Every sheet MUST be read, subject to FR-024's sheet-activation rule. A drawing with no display dimensions MUST be skipped coverage, and dimensions whose override flag, unit or value could not be read MUST be **unresolved** naming them. Ownership of the dimension by the model rather than by the drawing MUST NOT exclude it; the macro filtered on annotation type only, and an overridden model-item dimension is the defect being hunted.
- **FR-019**: `standards.drawing.annotations_not_dangling` MUST fail, at **error** severity, once per drawing document that has one or more annotations whose dangling flag is set, of **any** annotation type, naming every such annotation with its sheet, its view, its annotation type and its identity. Every sheet MUST be read, subject to FR-024's sheet-activation rule. A drawing with no annotations MUST be skipped coverage, and annotations whose dangling flag could not be read MUST be **unresolved** naming them.
- **FR-020**: `standards.drawing.revision_matches` MUST produce **warning**-severity findings, never errors, one per drawing document, naming every disagreement it found, in three cases: the drawing has no revision table on any sheet; the revision read from a revision table disagrees with the drawing's own revision property; the drawing's revision property disagrees with the revision property of a document any of its views reference. The revision MUST be read from the cell the profile names; a table whose last data row is still its header row (the profile's header text) MUST be read as the profile's initial-revision value. Comparison MUST be case-insensitive. **Every sheet's revision tables and every referenced document MUST be compared** (difference y), each disagreement naming both values and their source. The check MUST be **unresolved**, naming what was missing, when the revision property, the table contents or a referenced document could not be read, and for the model comparison when the drawing references no document.
- **FR-021**: `standards.drawing.no_itar_statement` MUST produce one **warning**-severity finding for a drawing document whose note text, anywhere on any sheet, in any view or sheet format, contains the profile's export-control phrase as a case-insensitive substring, naming every sheet and note that carried it. Absence of the phrase in readable notes MUST be checked coverage; a drawing with no notes MUST be skipped coverage; notes whose text could not be read MUST make the check **unresolved** naming them, because an unread note cannot be shown not to carry the statement.
- **FR-022**: `standards.document.data_card_complete` MUST be evaluated for every part, assembly and drawing document whose **file name** matches the profile's part-number pattern, and MUST fail, at **error** severity, once per document for which any of the profile's data-card property names is absent or resolves to a value that is empty or whitespace only, naming each such property and whether it was absent or blank. The pattern MUST be matched case-insensitively, as a whole-string match, against the file name **including its extension**, taken from the document's recorded path. The **resolved** value MUST be the one compared. A document whose file name does not match the pattern MUST be skipped coverage naming the convention; a profile with no pattern MUST make the check skipped coverage naming the empty setting; and a document whose custom properties could not be read MUST be **unresolved**.

**Evidence, the dump profile and IR additivity**

- **FR-023**: The checks MUST run over the evidence package, never live against SOLIDWORKS from the reasoning side, exactly as the feature 003 checks do. Signals the checks need that the package does not carry today MUST be added to the dump as **additive** IR fields: assembly exploded state, document-level rebuild-error count, mate-entity reference resolution status, component transparency override, **whether the component carries a component-level appearance override at all**, component visibility, **whether the component is a pattern instance**, sketch text-segment presence, part mass-override flag with the configuration the material and mass were read in, and cut-list items with their folder, body count and exclusion flag. (`contracts/ir-additions.md` section 1 is the normative field list and states their count; no other document repeats it.) **Every new field and every new model this feature introduces, including all of FR-024's**, MUST be optional, MUST carry a default, MUST be omitted when null, and MUST NOT appear in the required set; the IR schema minor version MUST be bumped once (1.3.0 to 1.4.0) in the C# and Python declarations together; the generated schema contract MUST be regenerated; and the feature 001, 002 and 003 golden fixtures MUST remain byte-identical.
- **FR-024**: The extractor MUST gain a native **drawing** dump phase producing, for a drawing document: its own custom properties; its sheets in order; each sheet's views with a name and the document each view references; each view's display dimensions with an identity, a name, the override flag, the override value and the unit that value is reported in; each view's annotations - **including those of the sheet-format (type-1) pseudo-view**, which is where a sheet's own annotations live and the only place the macro looked for the export-control statement - with an identity, a name, a type and a dangling flag; each sheet's revision tables with their rows and cell text, each row marked header or data; and each view's notes, again including the sheet-format pseudo-view's, with an identity and their text. Whether that pseudo-view is returned by the sheet's own view enumeration is a workstation probe (Assumptions); if it is not, the phase MUST enumerate views by the drawing's first-view walk instead, and a sheet that records no sheet-format view MUST make the export-control check **unresolved** for that sheet rather than checked. Drawing documents MUST enter the package's document list and manifest, and the design record's drawing document list MUST be populated. Each sheet MUST record the **source** that produced it - the native drawing phase or the Python PDF ingest - and the four drawing checks MUST evaluate natively dumped sheets only; a drawing whose only sheet evidence is PDF-ingested MUST be unresolved coverage naming the source, because a parser with known limits may not produce a demonstrated finding. The standing gap the extractor writes on every dump saying that drawing sheets come from the PDF ingest MUST be emitted only when the drawing phase did not run, and MUST name the profile that skipped it. Every value the phase could not read MUST be recorded as a gap naming it, per FR-029, rather than as an omitted field. **Sheet activation**: whether the views, dimensions, annotations, revision tables and notes of a non-active sheet can be enumerated without activating it is a workstation probe (Assumptions); if they cannot, the phase MUST record a gap per non-active sheet and every affected drawing check MUST be unresolved for those sheets. The phase MUST NOT activate a sheet to obtain evidence, per FR-044.
- **FR-025**: When the root document of a Standards dump is a **drawing**, the dump MUST also run the document, manifest, mate, feature, equation and cut-list phases over each document its views reference, and over every part and sub-assembly reachable through a referenced assembly's component tree, so that the part and assembly checks have evidence to grade - using only what is already loaded in the session. It MUST NOT open, load or resolve anything to do so (FR-044); a referenced document that is not loaded MUST be recorded as a gap naming it, and every part- and assembly-scope check for it is unresolved coverage naming that gap. The dump MUST NOT discover or extract the drawings of an open model: a model's drawings enter a package only when the drawing itself is the dumped document, or when the package was produced elsewhere and handed to the command line.
- **FR-026**: Every entity this feature emits into the IR - cut-list item, drawing sheet, drawing view, display dimension, annotation, revision **table**, note (the revision table's *rows* are carried inside the table and identified by their index within it, not separately) - MUST carry a **persistent reference** scoped to its document, emitted from day one, as the constitution requires of every IR entity. Where SOLIDWORKS offers no persistent reference for an entity kind, the package MUST record a stable identity for it and say which it is, so a consumer can tell a persistent reference from a within-dump identity and never presents the second as the first.
- **FR-027**: The extractor MUST offer a **`Standards`** dump profile that extends the existing reduced model-check profile with the phases the standards checks need (the cut-list phase, and the drawing phase and FR-025's referenced-model phases for a drawing) and still skips the phases they do not need. The existing `Full` profile MUST also run the cut-list phase, and the drawing phase for a drawing root, so a full extract is never less complete than a standards one. The package MUST record the profile that produced it and the phases it ran, and a consumer MUST be able to tell from those phase rows whether the standards evidence is present.
- **FR-028**: The reasoning side MUST be a sibling rule family beside the feature 003 family, reusing its rule-result type, its outcome and severity machinery, its coverage buckets, its result-to-report step, and its run-folder and carry-forward skeleton. Where feature 003 hard-codes its own family (the summary check id, the rule-scope values, the rules version), those MUST be **generalized** so that both families supply their own, rather than copied into a second implementation.
- **FR-029**: A signal the dump could not read MUST become an **unresolved** coverage row naming what was missing and why, and MUST never become a pass, a fail or a silent skip. This applies to every check in FR-007 to FR-022, which is why each of them names its unresolved condition explicitly.

**Severity, verdict and report**

- **FR-030**: Severities MUST be: **warning** for `standards.drawing.revision_matches` and `standards.drawing.no_itar_statement`, **error** for the other fourteen checks. Error findings MUST map to `demonstrated` findings and warnings to `suspected` findings, as feature 003 maps them; skipped, unresolved and out-of-scope results MUST be coverage, never findings with a verdict.
- **FR-031**: Every standards finding MUST name the check id as its check; the document it graded and the component instances that reach it as its components; each failing subject as an input carrying the subject's id, name, kind and persistent reference (or its recorded identity, per FR-026); the observed condition; the check's statement as its requirement; the recommended change; and the recording tool step as its tool result. It MUST carry the standard evidence fields of feature 001 - including the configuration the package was dumped in, and the profile's path and content hash in its coverage limits - **without changing the feature 001 finding contract**. Each subject MUST also appear in a structured subject array beside the finding in the route's response, carrying its persistent reference and scope document, so the page can act on it without parsing a display string, exactly as feature 003 requires of its own findings. A subject with no resolvable SOLIDWORKS entity MUST say so in that array, so the page renders no Show control for it rather than one that always fails.
- **FR-032**: The result MUST carry a **release verdict** computed from the error count and the unresolved coverage alone, and from nothing else: `not_ready` when the error count is greater than zero; `ready` when the error count is zero and no check has an unresolved row on any document; `ready_coverage_incomplete` when the error count is zero and one or more checks have an unresolved row. The counts in **every** bucket - error, warning, checked, skipped, unresolved, out of scope, and the number of findings waived by an active exception - MUST be rendered beside the verdict in every state, and the unresolved check ids MUST travel with the verdict in every state, not only in `ready_coverage_incomplete`, so an engineer never learns after a re-run that four checks never ran. A verdict of `ready` reached with waived findings, with checks skipped because a profile list was empty, or over a package that carried no drawing MUST say so on the headline. A letter grade MUST NOT be produced, and no single number may stand alone as the result.
- **FR-033**: Coverage MUST be recorded **per check per bucket per run as one aggregated item naming the documents it covers and the per-document reason**, replaced rather than duplicated when the check runs again - the rule feature 003 already holds to. The result MUST list all sixteen checks on every run, each showing every bucket it landed in with the documents and reasons in that bucket, so that a check that did not apply is visibly accounted for rather than absent; where a single line must stand for a check, the worst bucket it reached decides it, in the order unresolved, failed, warned, skipped, checked, out of scope, so no summary line claims coverage that is partly unknown. The report MUST state that no document was rebuilt and that rebuild-error counts are as the documents stood.

**The run folder, the tab and the routes**

- **FR-034**: Each standards check MUST write its own run folder through the same run-folder helper the review, the terminal and the model check use, MUST register that folder as the pane's latest run so entity resolution and the Ask tab read the same evidence, and MUST write a check record into it so the result can be read back by the folder's id after a restart. The check record MUST carry a **family** field distinguishing a standards record from a model check record; the field MUST be optional with a default that keeps existing model check records readable; reading a check by id MUST use that field to decide which family's result shape to return; and each host's latest-check field MUST be filtered by family, so a standards run never becomes the Model check tab's latest check. The record MUST identify the profile by path and content hash and MUST NOT copy any profile value into the record, the session, the report or any message to the page.
- **FR-035**: The Standards tab MUST be a sixth task-pane tab beside the five existing ones (Review, Ask, Extract, Model check, Remodel). No existing tab may be removed, hidden or reordered, and the MCP function list and the terminal profile's enabled tools MUST be unchanged, with the existing tests that pin those lists passing unedited. The family MAY register exactly one **review-only** check tool, because the shared run skeleton dispatches its checks through the tool registry with a session sink; every finding's recorded tool step MUST exist in the session it cites, and the report MUST cite no step that does not exist.
- **FR-036**: The Standards tab MUST carry a one-sentence purpose string rendered both as the tab's banner and as the tab's tooltip, as every other tab does, and that sentence MUST state that the tab needs no language model and no API key. The tab's content MUST be created on first activation from a named placeholder note, as the fourth and fifth tabs are, so a sixth renderer process is not started inside SOLIDWORKS at add-in load.
- **FR-037**: A package produced by the `Standards` profile MUST be recognisable to the pane's evidence step strip as partial evidence: the strip MUST name standards-only evidence and offer Extract full evidence, a standards run folder MUST never be suggested as the Extract tab's output folder, and a review handed a standards package MUST record a coverage item naming the phases the profile skipped - the rules feature 003 already states for its own reduced profile, generalized rather than restated for one profile name. The generalization MUST be driven by **whether the profile is a reduced one and by the package's own phase rows**, not by a second literal list of profile names, and the existing reduced profile's wording MUST NOT change.
- **FR-038**: The page-to-host message set MUST be: `ready`, answered with `init` carrying the backend port and origin, the token, the run root, the configured **profile path** (or null - the page shows which profile is in force and relays the path on the check route, since the reasoning side owns the schema), the open document and the latest **standards** check; `standards.start`, answered after the dump with `standards.extracted` carrying the run directory, the document, the configuration, the counts extracted and the gaps, or refused with a named error class when there is no document, the add-in is not attached, the document has never been saved, the document kind is not a part, an assembly or a drawing, or no readable profile is configured; and `entity.show`, `report.open`, `folder.open` and `log.open` **delegated to the shared pane actions**, byte-for-byte the rows the Model check page already has, with their tests parameterized over both hosts rather than duplicated. Host-to-page messages MUST be the existing unsolicited set - `status`, `document.changed` carrying the path, configuration and kind, and `backend.stopped` - with the existing `error` envelope and error-body shape. The page MUST call the backend itself with the token and origin it received, as the Model check page does.
- **FR-039**: The backend MUST expose the check as routes beside the existing model check routes: start a standards check over a run directory, read a check by id (answering both families per FR-034), and accept an exception for one finding. The routes MUST obey the existing token, origin, run-root path and error-body rules without restating them.
- **FR-040**: Every untrusted string the page renders MUST go through the shared DOM helpers that insert text as text, served from the same virtual host under the existing content security policy; the escaping rule MUST exist in exactly one place for all pane pages.

**Waivers and the command line**

- **FR-041**: An error-severity standards finding MUST be acceptable as an exception through the existing exception store. An acceptance waives the **check for that document**, not for one subject, and the Accept control's label MUST say so. The exception MUST be bound to the finding's document, its component instances, its configuration and a fingerprint covering every subject the check read, so that a newly appearing subject re-opens the finding for re-review rather than being silenced; this requires an additive **document binding** on the exception record, optional with a default so existing records load, because a drawing finding has no component instances and an unbound waiver would be the blanket exclusion the constitution prohibits. A required note MUST be enforced; an active exception MUST turn the result into checked coverage carrying the exception id and reason, never hide it; an exception whose fingerprint has changed MUST be flagged for re-review and MUST NOT silence the finding. Warning-severity checks MUST NOT be acceptable, and the Accept control MUST be **absent**, not disabled, for them. Accepted exceptions MUST survive the next run by both halves of the existing rule: the pane's run-folder carry-forward (a missing candidate is reported and is not an error; an unreadable candidate refuses the run), and, for the command line, the accept command writing `exceptions.json` beside the package, since a run folder the command line wrote is never a carry-forward candidate.
- **FR-042**: A flat waiver file mapping check ids to reasons MUST be importable against a run, accepting every matching error-severity finding at once. The status words MUST be the existing command's, generalized over the family: `accepted <n>` when the file is written, `would accept <n>` for a matching id on a run that writes nothing because another id was invalid, `unused` for an id that matched no finding, and `invalid (warning check)` / `invalid (unknown check)`. When any id is invalid the import MUST write nothing and exit 1; when every id is valid it MUST write the file and exit 0. This MUST reuse the existing waiver-import command by generalizing it over the family, not by adding a second implementation: one command body, with the family taken from the run record and the **command name treated as a guard on it** - a family-named command pointed at the other family's run MUST be refused naming both, rather than grading it. The status words themselves are a per-family fact, so the existing family's wording MUST NOT change.
- **FR-043**: The command line MUST offer `swreview check standards --package <dir> --out <dir> [--profile <yaml>] [--json]` with the same output-folder rule the other check commands hold to: the session, report and check record go to `--out`, and the package directory MUST only be read - grading a package MUST NOT edit it. It MUST refuse a package that does not record the phases the standards checks read, naming the profile that produced it and the missing phases, rather than reporting sixteen unresolved checks that read as a broken model; the test MUST be the phase rows the package records, not the profile's name, so any package that actually ran the phases is accepted. It MUST run through the same single evaluation entry point the route uses, print findings and coverage in both the human and JSON shapes the other check commands print, and **exit 1 on every validation error or refusal** (unreadable or missing package, missing phases, missing, unreadable or schema-invalid profile, unwritable `--out`) and **0 otherwise**, with violations in the output rather than in the exit code.

**Read-only and no language model**

- **FR-044**: Every document the checks touch MUST be treated as read-only. This feature MUST NOT rebuild anything: forced rebuild stays on the read-only guard's denylist and this feature adds no exception to it. Rebuild-error counts are read as the documents stand, and the report says so. The feature MUST NOT open, resolve, load, activate, suppress or save any document, MUST NOT change a sheet, a configuration or a display state to obtain evidence, and MUST NOT write a custom property. The dump's gate log MUST show zero mutating interop members, and no sheet-activation member, for a standards run.
- **FR-045**: No language model is involved anywhere in this feature. No provider may be constructed and no API key read on the check path, the tab path or the command-line path, and no call may be made to any host beyond the local backend the pane already talks to through its same-origin proxy. A test MUST prove it by making the provider factories raise.

### Key Entities

- **Standards Profile**: The company's configuration for the checks - vault root, library prefix lists (skip, one-mate, two-mate, sketch-exempt), data-card property names, part-number file-name pattern, revision property name, initial-revision value, revision-table header text, revision-table cell location, material configuration name, export-control phrase - with a documented schema, a placeholder example in the repository and the real file outside it.
- **Standards Check Run**: One execution: the package it read, the profile it read (by path and content hash, never by value, per FR-034), the run folder, the family, the timestamp, the results and the verdict.
- **Standards Check (rule)**: One of the sixteen, with its id, the document kind it applies to, the evidence fields it reads, its condition, its severity, its skip conditions and what makes it unresolved.
- **Checked Document**: A part, assembly or drawing document the traversal reached, with its kind, path, file name, configuration, the component instances that reach it, and whether its file name matches the part-number pattern.
- **Library Classification**: The derived mate requirement for a component - none, at least one, or at least two - from the longest prefix matching its path **within the mate-count lists**, resolved independently of the skip and sketch-exempt lists.
- **Cut List Item**: One cut-list item of a part with its persistent reference, its folder, its body count and whether it is excluded from the cut list.
- **Drawing Sheet**: One sheet with its persistent reference, its name and order, its evidence source (native or PDF ingest), its views, its annotations, its notes and its revision tables.
- **Drawing View**: One view with its persistent reference, its name, its sheet, the document it references, its display dimensions and its annotations.
- **Display Dimension**: One dimension on a view with its persistent reference, its name, its override flag, its override value and the unit that value is reported in.
- **Annotation**: One annotation on a view or sheet with its persistent reference, its name, its type and its dangling flag.
- **Revision Table**: One revision table on a sheet with its persistent reference and its rows; each row carries its index within the table, its cell text and whether it is the header row.
- **Note**: One note on a view or sheet format with its persistent reference and its text.
- **Data Card Field Result**: One profile property name on one document with its resolved value and its state: present, blank or absent.
- **Release Verdict**: `not_ready`, `ready` or `ready_coverage_incomplete`, with the counts in every bucket, the waived count, and the unresolved check ids.
- **Exception / Waiver**: The existing review exception, bound to a standards check id, its **document**, instances and configuration and a fingerprint of the check's inputs, with a required note; and the flat waiver file that creates many at once.

## Assumptions

- The macro's behaviour is taken from the reverse-engineering cited throughout and in Appendix A, which was produced from the macro dump and the owner's description document. Where the macro is buggy, this spec follows the documented intent and records the deviation in the Differences from the Macro table rather than reproducing the bug.
- The verdict's third state (`ready_coverage_incomplete`) is this spec's decision, not the macro's: the owner asked for "ready to release" only with zero errors, and the constitution forbids claiming a clean result over coverage that is unknown. The owner may collapse it into `not_ready`, or into `ready` with a caveat; the decision is recorded here so that it is a choice rather than an accident.
- The checks read whatever configuration the package was dumped in. A document dumped in a different configuration is named in the finding's coverage limits, as feature 003 already does, and the material check is unresolved when the configuration its material was read in is not the one the profile names.
- Sub-assembly mates are not extracted by the package in this version, so the mate-dependent parts of two checks are unresolved per sub-assembly. Extracting them is a separate change to the mate phase and is not in this feature's scope.
- The interop members the new reads need exist on the pilot's SOLIDWORKS version. Nothing is trusted on a real document before its probe passes. The workstation probes, each with what it settles, are: **(1)** which interface exposes the assembly exploded state; **(2)** the transparency-override polarity - which recorded value means transparent (SC-014); **(3)** the component visibility read; **(4)** the revision-table read - rows, cells and the header row; **(5)** the note walk across views and sheet formats; **(6)** the drawing-view and annotation walk, including annotation identity; **(7)** whether a non-active sheet's views, dimensions, annotations, revision tables and notes can be enumerated **without** activating it (FR-024's fallback depends on the answer); **(8)** the cut-list walk - which feature type names the cut-list folders carry on 2024 SP5 and whether the exclusion flag is readable without activating a body folder; **(9)** the sketch text-segment read, including on a sketch consumed by a hole-wizard feature; **(10)** which of this feature's new IR entity kinds SOLIDWORKS offers a persistent reference for (FR-026). These are listed again in `research.md` with the same content.
- The owner writes the real standards profile on the workstation at the path the quickstart names; the repository never sees it. The values the macro carried are listed in `research.md` as the starting point for that file.
- The evidence package is produced by the add-in in process, as the Model check tab's is; a package produced on another machine is graded identically by the command line, which is what makes the checks runnable without a licence.
- Exception semantics, the carry-forward rule, the run-folder naming, the pane message envelope, the error body, the token and origin rules, and the shared entity resolver are those of features 002 and 003 and are reused unchanged, except for the additive document binding on the exception record that FR-041 names; this spec restates only what differs.
- The shared entity resolver today resolves model entities (components and features) in the active or scope document. Whether it can select a drawing sheet, view, dimension or annotation is a question for the plan phase; until it can, those subjects are rendered with no Show control per FR-031, never with one that always fails.

## Out of Scope

- **Sketch visibility.** The macro never implemented it and recorded that the API offers only an all-on or all-off switch. Nothing here reads or reports it.
- **Assembly interference.** The macro's interference check is an empty placeholder; the reviewer already has its own interference tooling with its own exception semantics, and merging the two is a separate decision.
- **The EPDM API.** No vault API is used, as none is used anywhere else in this repository. Revision values come from the ordinary custom property the vault writes into the file, which is exactly what the macro read.
- **Force rebuild, and any other document mutation.** This feature adds no exception to the read-only rule; the two bounded exceptions in the constitution remain the only ones.
- **Removing, hiding or reordering any existing tab.** The Standards tab is added as the sixth, beside the Review, Ask, Extract, Model check and Remodel tabs; none of them changes.
- **Discovering a model's drawings.** A drawing enters a package only as the dumped document or from a package produced elsewhere; nothing here searches a vault for the drawings of an open assembly.
- **Any language model.** No provider, no prompt, no key and no call beyond the local backend on any path of this feature.
- **Fixing anything.** Like the macro, this feature reports; it never repairs a model, a drawing or a data card.
- **Extracting sub-assembly mates** and **configuration-specific data-card properties**. Each is named as a gap where a check needs it.
