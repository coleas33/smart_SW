**Purpose**: Validate specification completeness and quality before proceeding to planning

**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.

## Notes

- Validation iteration 1 (2026-09-17, against the spec as written after the design brief's binding decisions): all items pass with the accepted deviations below, each evaluated rather than waved through.
- Accepted deviations from "no implementation details" (CHK001, CHK003, CHK011, CHK026):
  - **Check ids** (`standards.assembly.not_exploded` and so on) appear because they are the engineer-facing names of the findings, the vocabulary of the waiver file and the strings the report and the tab display.
  - **IR field and model names** (`is_exploded`, `rebuild_error_count`, `transparency_raw`, `visibility_raw`, `text_segment_count`, `CutListItem`, `DrawingRecord` and the rest) appear in FR-023 and FR-024 because *what evidence must be captured* is the requirement; the field list itself is delegated to `contracts/ir-additions.md` and is not repeated in the spec.
  - **The IR schema version** (1.3.0 to 1.4.0) and the byte-identical golden rule appear because additivity with no regression is a stated constraint of the constitution, not an implementation choice.
  - **The exception store, the run folder, the shared DOM helpers, `PaneActions` and feature 003's rule machinery** are named because *reusing them rather than adding a second silence mechanism, a second escaping point or a second family implementation* is a requirement (FR-028, FR-034, FR-040, FR-041). Naming them is what makes the requirement testable.
  - **`TRANSPARENCY_POLARITY`** is named in FR-012 and SC-014 because the requirement is that the polarity is a single settled fact rather than an assumption spread across the checks, and that the check reports unresolved until it is settled.
  - **SC-004, SC-005, SC-009 and SC-010** name goldens, the provider factories, the gate log and the run folder because the regression gates, the no-leak gate, the read-back gate and the no-language-model gate are themselves stated success criteria; a technology-agnostic wording of them would not be measurable.
  - **SOLIDWORKS vocabulary** (exploded state, mate entities, constrained status, cut-list items, display dimensions, dangling annotations, revision tables, sheet-format views) appears throughout because the checks are defined over observable SOLIDWORKS state and the engineer reading a finding sees those words.
- Two decisions are recorded in the spec as decisions rather than left implicit, and both remain open to the owner without making the spec incomplete: the third verdict state `ready_coverage_incomplete` (Assumptions), and whether `research.md`'s "values the macro carried" table stays in a public repository at all (`research.md` R5's handling note).
- Validation iteration 2 (2026-09-17, re-run against the **completed plan package** — `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md` and `tasks.md` — after `/speckit-tasks`): CHK007, CHK008, CHK009, CHK010 and CHK021 were re-evaluated against what the artefacts actually say rather than against the intent, and each was restated to the true claim. CHK009's restatement was accompanied by an amendment to FR-012 in the spec, which now makes its checked condition explicitly conditional on the settled polarity. CHK021 is the one item whose second half is validated against `tasks.md` and therefore **could not** have been satisfied at the pre-planning gate; it is split above into a spec half and a tasks half so the gate each is measured at is visible.
- Items marked incomplete would require spec updates before `/speckit-clarify` or `/speckit-plan`; none is marked incomplete in either iteration. The tasks half of CHK021 is by construction a post-`/speckit-tasks` validation, not a pre-planning one.
