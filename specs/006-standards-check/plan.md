# Implementation Plan: Standards Check

**Branch**: `006-standards-check` | **Date**: 2026-09-17 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/006-standards-check/spec.md`

## Summary

Add a sixth task-pane tab, **Standards**, that grades the open document against the company's
release checklist - sixteen deterministic checks across parts, assemblies and drawings -
instantly, with no language model, no API key and no call beyond the local backend. The
checks run over the evidence package, never live against SOLIDWORKS from the reasoning side,
so this feature is three pieces:

1. **Extractor**: **ten** small additive reads on existing dumpers (exploded state,
   document-level rebuild-error count, mass-override boolean and the configuration the
   material was read in, mate-entity reference resolution, component transparency,
   appearance override, visibility and pattern-instance origin, sketch text segments) -
   the field rows and the count are `contracts/ir-additions.md` section 1, which nothing
   else repeats - one new **cut-list** phase, one new **drawing** phase
   over a document kind the extractor has never read, a `Standards` dump profile that extends
   `ModelCheck`, and a drawing-rooted traversal that reaches the models a drawing's views
   reference. IR 1.3.0 to 1.4.0, every addition optional, defaulted and omitted when null.
2. **Reasoning**: a sibling rule family `checks/standards/*` beside `checks/rms/*`. The
   machinery feature 003 built - `RuleResult`, the outcome and severity mapping, the coverage
   buckets, `report_results`, the run folder, the carry-forward, the check record - is
   **generalized into `checks/rules/`** and supplied with a family descriptor by each of the
   two families, rather than copied. Company-specific values never enter the code: they come
   from a **standards profile** file outside this repository, validated in one place.
3. **Pane and command line**: a sixth tab that mirrors the Model check tab byte-for-byte
   wherever the behaviour is the same, `POST /checks/standards` beside `/checks/rms`,
   `GET /checks/{check_id}` answering both families through a new `family` field on the check
   record, and `swreview check standards --package <dir> --out <dir> [--profile <yaml>]`.

The checks' meaning comes from a 2017 VBA release-checklist macro, reverse-engineered; where
the macro is buggy this feature follows the documented intent and records the deviation. The
macro force-rebuilt every drawing; this feature rebuilds nothing, and the report says so.

## Technical Context

**Language/Version**: C# on .NET Framework 4.8 x64 (extractor dump, drawing phase, cut-list
phase, probe; add-in host and page); Python 3.11+ (profile schema, rules, tools, routes, CLI).

**Primary Dependencies**: No new packages on either side. C#: existing interop, `SwGate` and
`ICallGuard`, `GapCollector`, `PackageWriter` (two new phases, a drawing branch in
`DocumentPaths` and `BuildDesign`), `ComponentTreeDumper` (four new reads and a drawing-root
forest), `PropertyDumper` (four new reads), `MateDumper` (one new read), `FeatureDumper` (one
new read), `ManifestBuilder` (drawing entries), `ReadOnlyGuard` (the new denied members
enumerated in research R8), plus the new `CutListDumper`, `DrawingDumper` and
`DrawingTraversal`; in the add-in, `PaneActions`, `IPageChannel`/`PageChannel`, `SwReviewDump`
and `RunPackageIndex` are **reused unchanged**; `web/shared/dom.js` is reused unchanged and
joined by a new `web/shared/check-page.js` and `check-page.css` extracted from the Model check
page; and `TaskPaneControl`, `StepStrip`, `SwReviewAddIn`, `UserSettings`, `RunFolders` (one
new factory method **and a newest-run scan that does not exist today**) and `ModelCheckHost`
are edited. Python: `pydantic`, `pyyaml` (both already present), the existing `checks/rms/`
machinery moved to `checks/rules/`, `exceptions.py` (one additive field, one new fingerprint
kind and a document-scoped fingerprint / accept / match path), `agent/runner.py` (the
reduced-profile coverage sentence generalized), `tools/registry.py` (**one new registration
function, outside `REGISTRATIONS`**), `tools/context.py` unchanged, `chat/server.py` (three
routes), `cli.py` (two commands).

**Storage**: Files only. `package.json` (two new arrays, the new fields enumerated in
`contracts/ir-additions.md` section 1, two new phase rows), `exceptions.json` (existing shape plus one optional field),
`<run_root>/<yyyyMMdd-HHmmss>-<doc>-standards/{package.json, exceptions.json, session.json,
report.md, check.json}`, and one file this repository never sees: the owner's standards
profile at the settings path, default `%LOCALAPPDATA%\SwReview\standards.yaml`.

**Testing**: pytest per check over synthetic packages from a builder
(`reviewer/tests/support/standards.py`), goldens generated by the same builder, **two
fictional profile fixtures** whose values differ in every field so that a compiled-in value
fails (SC-005); xUnit for `DrawingTraversal` and `CutListDumper`/`DrawingDumper` over fakes,
for the guard denylist, for the ten new dumper reads, and for `StandardsHost` over the fake
channel and seams `ModelCheckHostTests` already uses; page contract and injection tests for
the Standards page; in-process ASGI client tests for the three routes; a marked perf test
(SC-011); ten workstation probes per `quickstart.md` (SC-012 to SC-016).

**Target Platform**: as features 001, 002 and 003. The reasoning side runs with no SOLIDWORKS
licence, which is what makes `swreview check standards` runnable in CI and on cheap machines.

**Project Type**: extends both trees.

**Performance Goals**: evaluating all sixteen checks over a fixture package representing a
200-component assembly with three drawings completes in **under 2 s** on the CI machine
(SC-011, a marked perf test). On the pilot workstation, pressing Standards on a 40-component
assembly returns a rendered verdict in **under 10 s** end to end, and the standards additions
add **under 10 s** to the reduced-profile dump of the 200-component pilot assembly (SC-012);
the drawing phase reads a six-sheet drawing in **under 10 s** (SC-013). The workstation
numbers are targets measured on the test day, not estimates this plan has verified.

**Constraints**: read-only, and this feature adds **no** exception to the constitution's rule
- `ForceRebuild3` stays denied, and the further mutating and view-changing members enumerated
in research R8 join the denylist, so the movement is a narrowing exactly as feature 003's was; no language model
anywhere on any path; IR additions additive with the feature 001, 002 and 003 goldens
byte-identical; no company-specific value in any source file, test, fixture, golden, contract
or example profile, with `research.md` the single documented exception; the MCP function list
and the terminal profile's `enabled_tools` do not move, and the tests that pin them pass
unedited; no existing tab is removed, hidden or reordered.

**Scale/Scope**: assemblies to 500 components, parts to 1000 features, drawings to 20 sheets.
Sixteen checks, four user stories, two new dump phases, ten workstation probes.

**Structure Decision**. Three decisions carry the shape above.

1. **The extractor stays a recorder.** It writes raw numbers and raw type names - the
   transparency slot verbatim, the visibility integer verbatim, the exploded boolean, the
   what's-wrong count, the sketch text-segment count, the cut-list exclusion flag, the
   revision-table cell text - and classifies nothing. Every judgement that could be
   company-specific or version-specific lives in Python: the profile, the prefix matching, the
   part-number pattern, the transparency polarity, the header-row rule. Recalibration for a
   different SOLIDWORKS version or a different company touches YAML, a Python constant and
   tests, never C#. This is feature 003's decision, and following it is why the extractor
   holds no profile value at all - the host checks that a profile path is **configured and
   readable** and nothing more (FR-002).

2. **One family-neutral machinery, two families.** `checks/rms/{results,report,run}.py` and
   the three hard-codings in `registry.py` move to `checks/rules/`, and each family supplies a
   `CheckFamily` descriptor holding its name, its summary check id, its rules version, its
   scope vocabulary and its tool names. `checks/rms` keeps the same module paths as thin
   shims that import the moved names and bind `RMS_FAMILY`, so **every existing
   `reviewer/tests/unit/test_rms_*.py` and every golden passes with no edits** - that is the
   regression proof for the move, and a task asserts it before the standards family is
   written. The rejected alternative is a second implementation in `checks/standards/` that
   copies the outcome mapping, the coverage aggregation and the run-folder skeleton: it is
   about 700 lines of duplication of exactly the logic that decides whether an unknown is
   reported, and the constitution's DRY rule names this case ("repeated logic across checks
   MUST be extracted once it appears twice with the same intent"). A third alternative -
   `checks/standards` importing from `checks/rms` - is rejected because it makes one family
   depend on the other's name for no reason.

3. **A third pane host, sharing one collaborator with the second - and still not a `PaneHost`
   base class over all four.** A shared abstract base over the **four** hosts stays rejected
   for the reason feature 003 gave: `ReviewHost` needs backend chat state, `RemodelHost` needs
   a seat and a pipeline, and inheritance would drag all four sets of dependencies into one
   type. But that argument is about the two hosts that are **not** in question, and its own
   last clause - "`ModelCheckHost` and `StandardsHost` need neither" - is the argument *for*
   sharing between the two that are. `ModelCheckHost` is 427 lines of which roughly 250 are
   family-neutral plumbing (`Receive`, `Dispatch`, `Post`, `PostStatus`, `DocumentChanged`,
   `TrackCheck`, `FindCheck`, `SendInit`, `DocumentPayload`, `Dispose`; `:239` already
   delegates the four shared rows to `PaneActions`), and only `StartCheck` and the scope
   constant are its own. Re-implementing those 250 lines in `StandardsHost` is the second
   largest copy this feature could make, and Principle V names the case.

   So: `Review/CheckPaneHost.cs` is a **collaborator both check hosts hold**, not a base class
   - composition keeps the rejection of inheritance intact and keeps each host's own
   dependencies explicit. It carries the plumbing above and one start step supplied by its
   owner; `ModelCheckHost` and `StandardsHost` keep their own start verb, their own refusals
   and share one check record (folder name, directory, timestamp) held by the collaborator, because two identical three-field records in two namespaces would be exactly the copy the collaborator exists to prevent (decided 2026-09-17). The gate is the same one RK-7 uses for the Python move:
   **`ModelCheckHostTests` passes unedited** after `ModelCheckHost` is rebuilt on the
   collaborator, and that is its own task with none of this feature's own code in it. The four
   shared actions stay **delegated to `PaneActions`**, which is not edited, and its tests are
   added to the existing parameterization so the rows are proven identical across three hosts.

   **The page is the same story, and the larger half of it.** `Model/ModelCheckPage/check.js`
   is 1117 lines and `check.css` 217, and at least forty of check.js's fifty-five functions are
   family-neutral: the host channel (`send`, `onHostMessage`, `asError`, `handleUnsolicited`),
   the authenticated `call` wrapper and `backendError`, `loadLatestCheck`, `acceptRule`,
   `refreshResult`, `markAccepted`, `showSubject`, `cycleSubject`, `renderCarriedForward`,
   `renderFilters`, `countByBucket`, `documentSection`, `bucketGroup`, `subjectList`,
   `subjectLine`, `subjectMeta`, `toggleBucket`, `applyFilter`, `renderBackendState`,
   `showStatus`, `folderName`. Only `renderGrade` and `gradeHeading` are family-specific.
   A **named extraction task before US3** moves that half into `web/shared/check-page.js` and
   the shared rules of `check.css` into `web/shared/check-page.css`, leaving each page a header
   renderer (grade versus verdict) and its own start verb. It is gated the way the Python move
   is: **the existing Model check page contract and injection tests pass unedited.** The
   Standards page is then a separate folder under the same virtual host with the same CSP, and
   it renders every untrusted string through `web/shared/dom.js` (FR-040).

## Phase 0 and Phase 1

Research in [research.md](research.md) (R1 to R10). Design in
[data-model.md](data-model.md) and [contracts/](contracts/). Eleven points tasks must honour:

1. **The profile has exactly one schema owner, and no fallback.** `checks/standards/profile.py`
   is it. The host checks a path is configured and the file is readable and refuses **before**
   it creates a run folder or dumps anything; the backend validates the schema and returns the
   named error; a run folder created before that refusal is reported as an empty run, not as a
   result (FR-002). There are no built-in company values to fall back to, by construction:
   a fallback would grade a document against the wrong standard in silence, which is the worst
   failure a release gate has.
2. **Each document is graded once.** `checks/standards/traversal.py` decides the set: the root
   document, every part and sub-assembly document reachable through the component tree, and -
   for a drawing root - every document a view references plus everything reachable through a
   referenced assembly's tree, deduplicated by `document_id`. Each failing check produces
   **exactly one finding per document**, naming every subject and every instance that reaches
   it, and contributing one to its severity count (FR-003, difference a and difference n). The
   macro's unused deduplication collection is the author's unfinished intent; this is it,
   finished.
3. **One rule for unresolved instances, cited and never restated.** FR-005 splits on where the
   evidence lives: a check whose evidence comes from the instance's **referenced document** is
   unresolved for it; a check whose subject is the **instance itself** does not take it as a
   subject and names it in **skipped** coverage. `contracts/rules.md` cites FR-005 per check
   rather than repeating it, so the two halves cannot drift apart.
4. **Prefix matching is four independent questions, and one rule settles all of them.** The
   skip list, the sketch-exempt list, the one-mate list and the two-mate list are matched
   independently over the same path; within one list the longest match wins and every match in
   that list is named in the reason, and **across the two mate-count lists the longest match
   wins too**, the one-mate requirement taking an exact-length tie (FR-006). This replaces the
   macro's accident, where the one-mate list happened to be tested before the two-mate list and
   a catch-all folder relied on that ordering. An **empty** list is the opposite of a skip: an
   exemption list that is empty exempts nothing, so its checks run on every document they apply
   to; only the settings that *select* what to check (`data_card.properties`,
   `part_number.pattern`, `revision.property`, `export_control.phrase`) make a check skipped
   when they are empty (`contracts/rules.md`).
5. **Nothing is rebuilt, and nothing is activated.** `ISheet.GetViews()` is what lets the
   drawing phase read every sheet without activating one (verified present; whether a
   non-active sheet's contents come back populated is PROBE-7). If the probe says they do not,
   the phase records a gap per non-active sheet and the affected checks are unresolved for
   those sheets - it does **not** activate the sheet (FR-024, FR-044). The new denylist members
   of research R8 make that a refusal rather than a convention. Whether `GetViews()` returns the
   **type-1 sheet-format pseudo-view** - the only place the macro ever found the export-control
   statement - is PROBE-5 and PROBE-7 as well; `IDrawingDoc.GetFirstView()` / `GetNextView()` is
   the named fallback enumeration, and until the probe answers a sheet with no type-1 view makes
   `standards.drawing.no_itar_statement` unresolved rather than checked.
6. **The transparency polarity is a probe answer, held in one named constant.**
   `checks/standards/assembly.py` carries `TRANSPARENCY_POLARITY`, whose value is `unsettled`
   until PROBE-2 answers, and while it is `unsettled` the check reports unresolved on fixtures
   and on the workstation alike (FR-012, difference d, SC-014). One constant, one task to flip
   it, one fixture expectation to update - and the value is not company-specific, so it belongs
   in code rather than in the profile.
7. **Two new phases, recorded whether they ran or not.** `cutlist` and `drawing` join
   `PackageWriter.PhaseOrder`, so every package written after this feature carries two more
   phase rows - `skipped` for a profile that does not run them. The command line's refusal
   (FR-043) tests **the phase rows**, not the profile name, so a package that actually ran the
   phases is accepted whatever profile produced it. The cost is that the phase list in a
   package grows by two rows: golden fixture files on disk are static and stay byte-identical,
   but the tests that pin the full phase list are edited in the task that adds the phases, and
   that edit is named there rather than discovered.
8. **The check record grows a `family` field, the folder grows a suffix, and the newest-run
   scan is written from scratch.** The field is optional with the default `"rms"`, so every
   model check record already written still reads, and it is what `GET /checks/{check_id}` uses
   to decide which family's shape to return (FR-034). **There is no latest-check scan today**:
   `ModelCheckHost.LatestCheck` is in-process state set by `TrackCheck` and nulled in
   `Dispose`, and nothing in the add-in enumerates the run root, so reading a check back after a
   restart (AS-17, SC-009) is new work - `RunFolders.NewestCheckFolder(runRoot, suffix)`, called
   on `init` by both check hosts. Given that scan, the folder suffix (`-standards` beside
   `-check`) is what lets it answer for each host **from the folder names alone**; the
   alternative - one suffix and a `check.json` read per sibling folder on every `init` - is
   rejected because `init` runs on every tab activation. Two mechanisms, two questions.

9. **The 1.4.0 bump has three named consequences, not one.** (a) The version string is pinned
   in eight Python tests and four C# files, listed in the Source Code block above; the bump task
   edits exactly those pins and nothing else. (b) `schema_version` is an input to feature 005's
   package-reuse key, so **every package dumped before 1.4.0 stops matching for reuse** and the
   next pilot run re-dumps instead of reusing - correct, because the schema differs, and stated
   so nobody debugs it. The two pinned cross-language canonical-form strings and
   `ReuseFixture.cs` change in that same commit, because the Python pin follows `SCHEMA_VERSION`
   while the C# fixture hard-codes the literal, so editing one side alone breaks the agreement
   silently. (c) `ExtractorInfo.profile` is a **closed enumeration** on both sides, so adding
   `"standards"` is an enum extension in `ir/models.py` and `Dump/DumpContracts.cs` together, it
   changes the `enum` array in the regenerated contract, and a pre-1.4.0 reader refuses a
   standards package outright - which is intended.
11. **Six things this feature consumes rather than re-creates**, each built by feature 003 and
   each therefore gaining a second consumer here: `PaneActions`, `RunFolders`,
   `web/shared/dom.js`, the `SwEntityResolver` + `FeatureSelection` pair behind
   `entity.show`, the `ExceptionStore` carry-forward, and the run-folder + check-record
   skeleton. This list is the DRY contract between the two features, and it belongs in the
   plan so that a later change to any of them is known to have two consumers.
