# Tasks: The Engineer's Workspace

**Input**: Design documents from `/specs/009-engineer-workspace/` (`spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`)

**Prerequisites**: features 001 to 007 on main. User Stories 1 and 2 landed on main on 2026-09-23 (`2c48e2b`, `cf3c66e`, `b5cfcb4`) and are recorded as done in Phase 1. Feature 008 (`specs/008-checks-first-review/`) is being implemented beside this feature: every task below that needs one of its deliverables names the 008 task id and starts from main after that task has landed. Feature 010 (`specs/010-mechanical-checks/`) is being planned and implemented beside this one: the contacts backend (T018 to T019) waits for 010 T020 (the `Contact` model and `ReviewSession.contacts`, 010 data model section 9) and shows real contacts once 010 T022 (the contact path in `check_interference_group`) has landed; the session-contract edit (T034) is serial with 010 T020; the title change (T062) is serial with 010 T016 and T043, which regenerate golden baselines too; 010's new check ids (its T037, T047, T061, T067, T075 classify them in the policy) all fall under this feature's goal prefixes (research R2.4). 010's task ids were read from its `tasks.md` while it was being written on 2026-09-23; re-verify them before starting a dependent task.

**Tests**: REQUIRED, and **strictly test-first**: every implementation task is preceded by the test task that must be written and must fail first. Four acceptance tasks (T022, T032, T045, T058) are written after their implementation and pass with no further production code; if one is red, the defect is fixed in the task that owns the module and recorded in its commit. The tests that go red **by design** are named in the task that lands each change (research R2.20, R2.21, R2.23, R2.26) and edited deliberately there, never loosened. What must not move: `attention.json` bytes and both check bodies (R2.2), `report.md` and its `.md` goldens, `chat-events.schema.json`, `ir.schema.json`, `settings.schema.json`, `UserSettings.cs`, feature 008's `usageLine` body, `PageRuleScanTests` (passes unedited: no page script sorts or compares), `test_docstring_split.py` and `test_prefix_stability.py` (pass unedited).

**Organization**: Phase 1 records the landed User Stories 1 and 2. Phase 2 (Setup) lands the two shared backend pieces - the names helper and the words file. Then one phase per story in priority order: US3 the summary (backend first, then the page), US4 questions (the short form, then the page, after 008's batch route), US5 Results or Transcript, US6 sessions (backend routes, host rows, the configuration event, the page), US7 plain words. Then Polish, and Phase 9 for the next workstation sitting (SC-007).

## Format: `[ID] [P?] [Story] [lane] Description`

- **[P]**: can run in parallel (different files, no dependency on another unfinished task)
- **[Story]**: `US1` to `US7`; Setup and Polish tasks carry no story tag
- **[lane]**, for parallel dispatch against 008's and 010's implementation agents:
  - **[py]** touches `reviewer/` only (plus the contract files of other features it names)
  - **[page]** touches only the pane's page files - `extractor/SwReview.AddIn/Review/ReviewPage/*`, `web/shared/*`, `Model/ModelCheckPage/*` - and their C# page tests under `extractor/SwReview.AddIn.Tests/`
  - **[host]** touches the add-in's C# production files outside the page folders (`Review/ReviewHost.cs`, `Review/PaneActions.cs`, `Review/ReviewServices.cs`, `Review/SwEntityResolver.cs`, `Review/RunPackageIndex.cs`, `SwReviewAddIn.cs`, one new file) and their C# tests
- **[W]**: needs the pilot workstation or a licensed SOLIDWORKS seat - only Phase 9
- **[K]**: needs a provider key - only Phase 9

## Path Conventions

- Python: `reviewer/src/swreview/`, tests in `reviewer/tests/`; commands run from `reviewer/` with `uv run`
- C#: `extractor/SwReview.AddIn/`, tests in `extractor/SwReview.AddIn.Tests/`; `dotnet test extractor/SwReview.sln -c Release` (the offscreen WebView2 page suites included)
- Contracts: `specs/009-engineer-workspace/contracts/` (written by the plan; a task that lands a behaviour reconciles its contract if the code had to differ); other features' contracts are edited in the task that changes their shape

## Notes

- **The backend decides; the page prints.** Every count, group, order, label and sentence in these stories comes from `report/summary.py`, `review_words_v1.yaml` or an existing backend field. A page task that needs a number or a word the backend does not send stops and adds it to the backend in a [py] task; it never computes one. `PageRuleScanTests` is never edited to let a change through.
- **Findings do not change; their presentation does.** Titles become whole and named, ids move into folds, words come from labels. `observed`, `component_ids`, inputs, statuses and the ranking never change, and every id stays in a fold, the transcript and the report.
- **An older backend, an older session.** Every new field is optional and every page surface falls back to exactly what it showed before this feature (FR-030); each story has a test for that.
- **One of each.** One names helper, one words file, one summary function, one snapshot builder serving three routes and the page fixture, one render path for a live turn's end and a restore, one run-folder lookup for `report.open`, `folder.open` and `entity.show`.
- **Feature 008's code is called, not changed**, except the one `request_id` field on two error bodies (T042), and `usageLine`'s body is never touched.
- **The recordings stay off the repository.** The page fixture is generated from 008's committed fictional fixture; no recorded path or name enters a commit.
